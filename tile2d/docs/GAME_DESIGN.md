# 矿场自动化游戏 —— 需求与工程约束（工作稿）

> **本文档不预设游戏内容。** 资源、结构、需求的具体形式、配方、建筑、剧情、数值全部由设计者
> 提供，本文档只记录：① 已明确的需求；② 由这些需求推导出的工程约束；③ 需要设计者补充的内容清单。
> 模块与可执行文件用 `mine` 作临时名（来自"矿场"），最终命名随游戏定名一起改。

---

## 1. 已确认的需求（设计者原话，权威）

1. 游戏类型：**沙盒 / 工业自动化**。
2. 视角：**平面 2D**，不是横版。
3. 游戏内部存在一个**矿场**。
4. 矿场**有多层**。
5. **每层会生成不同的资源和结构**。
6. **每层会有一个或多个需求**。
7. 需求需要**通过特定方式提交原料或产物**。
8. 需求完成后**进入下一层**。
9. 存在两种模式：
   * **故事模式**：预先设定好的流程。
   * **无尽模式**：程序生成内容。
10. **贴图采用多边形风格**。
11. **没有玩家角色，所有玩家使用上帝视角操作游戏**。

12. **地块**：地图中**占据格子的固定物体**，包括地板、矿物、机器等。为保证之后的玩法，需要支持
    **2×2、3×3、2×3** 之类的大型结构地块。
13. **为了性能，地块分为两类**：
    * **场景地块**（场景、矿物、地板等）：**仅在需要时更新**；
    * **实体地块**（功能地块，例如机器）：**每 tick 或每 xx 秒更新**。

14. **实体地块继承场景地块**；**地块基类带一个布尔属性 `random_reverse`**，为真时在**地图初始化**时
    随机设定自身渲染：有 **50%** 的概率将自己**左右翻转渲染**。

15. **`random_reverse` 由内容作者定义**（写进内容数据），**`mirrored` 无需进入存档**；
    引擎会读的字段因此有两个：`image` 与 `random_reverse`。
16. **新增 `Floor` 类继承 `SceneTile`**，只多一个**地板标记**（告诉其他东西"我是地板"），
    并要有**对应的 `.ecfg` 定义器**（`floor::` 表）。
17. **第一份本体内容：泥地**（`floor:: dirt::`），贴图 `floor_dirt.png`。

18. **美术资源**：泥地的 `random_reverse` 为 **true**；**每个内容一个图片，不使用大图集**；
    命名不限，**官方内容包使用蛇形命名**；尺寸按需要**每 1 格 128 或 256 像素**，可以为其它值。
    （这就是 §7.13 的答案。）

19. **单矿物与散点生成器**（原话）："添加一个 single_ore（单矿物）类继承场景地块，层创建器添加
    散点生成器，以散点形式在指定 tile 层放置指定物体，包含最小生成数量，最大生成数量，平均密度，
    地板限制等属性。"

20. **左上角显示当前层数**（原话）："正式游戏中需要在左上角显示当前层数，格式为层1/层2"。

21. **故事模式第一层的内容**（原话）："设置故事模式第一层地图100*100,生成矿物石头，20-35个，贴图为给出图片"。
    本体内容因此有了**第一层**（`content/layers.ecfg`：100×100、地板是本体自己的泥地、散点撒石头 20–35 块）
    与**第一块矿物**（`content/ores.ecfg`：`ore:: stone::`，贴图 `content/art/ore_stone.png`）。这是设计者
    第一次给本体内容写数据，用的就是夹具与文档一直在演示的那套格式（§4、`docs/MODS.md` §0）。

22. **物品类与物品 ecfg 注册器**（原话）："添加物品类和物品ecfg注册器"。物品是**不在图上**的内容——机器
    产出、配方进出、需求点名、玩家携带的都是它——所以它有自己的一类（`mine::types::Item`）与自己的定义器
    （`item::` 表，`types/item_definition.h`）；引擎为它读的字段只有 `image`（§4、`docs/TYPES.md` §6）。

23. **第一件物品：石头**（原话）："创建物品石头 id=stone"。本体内容因此有了第一件物品
    （`content/items.ecfg`：`item:: stone::`，贴图 `content/art/item_stone.png`，64×64）。它与第一块矿物
    **同名而不冲突**：名字按**种类**发号，矿物是地图上占着格子的一格、物品是能被搬走的东西（§7.2 的第一项）。

24. **实体类与四叉树**（原话）："添加实体类，位置不与瓦片地图对齐，可以移动，交互，默认每tick更新除非
    特别声明更新间隔或不自动更新。为了保证性能，一个层运行时所有实体编入一个四叉树表便于快速检索一个位置
    一定范围内的实体"。（这一条先写成"位置不固定与瓦片地图对齐"，随即更正为"位置**不**与瓦片地图对齐"——
    按更正后的为准：位置是自由的，瓦片地图只是它旁边的参照，不是它脚下的格子。）

25. **掉落物类与定义器**（原话）："添加掉落物类和定义器，不自动更新，可以被鼠标拖动移动"。掉落物是
    **躺在地上、自己不变化、能被指针拖着走**的东西：它是实体的一种（§1.24），所以位置是自由的、进四叉树、
    能被查到；它有自己的 `drop::` 表，引擎为它读的字段是 `image`。

26. **钻头**（原话）："添加一个钻头类，类型为实体地块，可以被放置在矿物上，按照定义器设定的挖掘能力/矿物硬度
    计算时间，每段时间向外丢出一个矿物对应的掉落"。所以：钻头是**实体地块**（会跑的功能地块，§1.13），
    它站在矿**上面**（矿在它下面的瓦片层——一个格子每层只放一个地块，§1.12）；出一个掉落要多久 =
    矿的**硬度** ÷ 钻头的**挖掘能力**；时间到了就往外丢一个**那条矿对应的掉落物**（§1.25）。

27. **仓库**（原话）："添加仓库，类型为场景地块，通过定义器设定容量等参数，鼠标拖动掉落物到仓库上方即可把
    掉落物加入到仓库中，点击在地块右下角显示包含内部物品信息的ui，仓库对象中包含子对象container用于存储物品
    信息和处理存储功能并便于和其他代码交互，包含draginto子对象用于接收掉落物，包含click子对象接收点击信息"。
    拆开就是：**场景地块**（不跑、不自动更新）、定义器给**容量**、拖过来的掉落物进**容器**、点一下就在**地块
    右下角**看里面有什么；而 `container` / `draginto` / `click` 三个子对象各管一件事，并且都能被别的代码直接用。

28. **石头仓库与物品信息的显示**（原话）："我已经放置了贴图，添加一个石头仓库方块，容量100.以及我希望显示物品
    信息时包含物品的贴图，即[物品贴图][物品的本地化名称][数量]"。本体内容因此多了一个仓库
    （`content/warehouses.ecfg`：`warehouse:: stone::`，贴图 `content/art/capacity_stone_warehouse.png`——
    设计者自己放进本体包的那张，容量 **100**）；而仓库面板的每一行从此是
    **[贴图][本地化名称][数量]**：贴图是这条内容自己的那张，名称来自界面字符串表
    （`content.name.<种类>.<名字>`，其次 `content.name.<名字>`，都没有就显示注册表里的 id，`docs/TEXT.md`）。

29. **本地化名称功能**（原话）："添加本地化名称功能"。内容的名字是设计者写的 **id**（`stone`、`chunk`、
    `entrance`）——id 是存档与数据引用的东西，不是给人读的标签；界面上凡是显示一条内容的地方，现在都显示
    **本地化名称**：字符串表里有就用它，没有就用注册表里的名字（内容没了就是 `#<id>`）。查找只有一条链
    （`content.name.<种类>.<名字>` → `content.name.<名字>` → 注册表名字），实现在 `mine/content_name.h`
    的 `content_label()`，游戏里唯一的入口是 `MineApp::content_name(种类, id)`；**种类自己的词**
    （`ore`、`warehouse`…）是引擎的英文词汇，**不跟语言走**（设计者 M2.16 确认：不需要）。

30. **限制摄像头缩放为 40px-100px**（原话）："限制摄像头缩放为40px-100px"。游戏世界视图的相机因此只能把
    一格画成 **40–100 像素**：`mine/view_limits.h` 的 `kMinViewZoom = 40` / `kMaxViewZoom = 100`，
    在 `MineApp` 构造时交给相机（`set_zoom_limits`），所以**每一条**改缩放的路都受同一对数字约束——
    启动参数 `--view`、进层的自动取景、`+`/`-` 键、滚轮。40 是**还能看清并点中一格**的下限（再小一格
    只是一个点，指针挑不出来），100 是**一格占满屏幕**的上限；沙盒的相机是调试工具，仍保留自己的
    0.05–512（`docs/SANDBOX.md` §7）。这两个数是**常量**，不是内容数据：设计者 M2.16 确认不需要每层
    不同的范围。

31. **双击选中，上方居中显示物品信息**（原话）："使得包含container子对象的地块可以被鼠标双击选中，选中后会
    在游戏界面最上方居中显示物品信息"。拆开就是两条：**能被选中的是任何带 `container` 子对象的地块**——
    不是"仓库"一种，所以 `SceneTile` 多了一个问法 `container()`（默认 nullptr，仓库覆盖它，将来的机器输入侧也
    一样）；**双击**是选中的动作，落在有容器的地块上就选中它，落在别处（地板、矿、空地）就清掉选中。选中的
    地块把容器内容显示在**游戏界面最上方居中**：标题是它自己的本地化名字与"已用 / 容量"，下面每行
    **[贴图][名字][数量]**——与右下角面板同一份内容、同一个排版函数，只有位置不同。**一个指针一次只显示
    一处**：双击的第一次按下仍然是单击（右下角面板，§1.27），第二次按下选中、并把右下角的面板关掉；之后
    任何一次单击都把显示让回给右下角面板。双击的窗口是 0.4 秒（`mine/double_click.h` 的常量，不是内容）。
    设计者 M2.17 的三条补充：**"沙盒除了试玩部分需要该功能其他不需要"**——所以沙盒的**试玩**（按 `P` 进入的
    那个视图）也能双击选中，编辑状态不选；**"只需要装了什么就可以"**——面板只说容器里有什么，不说它是从
    哪来的（§7.10 的数据）；**"添加方框高亮提示"**——被选中的地块在**地图上**也标出来：占地大小的方框 +
    里面一层浅色（一格就是一格）。试玩里能被选中的是**能放在格子上的**内容，仓库现在是其中之一。
32. **`.ecfg` 的 `__include`**（原话）："为ecfg添加__include: #file 功能，加载时可以加载其他ecfg文件的内容
    放入include所在的位置解析"。所以：**一行 `__include: #<路径>` 被那个文件的内容替换掉，然后才解析**——
    不是"读进来当字符串"，也不是"另开一个文档"，而是**这一行的位置上就是那些行**。路径相对**写它的那个
    文件**（与内容文件引用美术资源同一条规则，`docs/MODS.md` §0）。被包含的文件顶格写，落进来时缩进到
    `__include` 那一行的缩进——所以一份片段能放进任何位置：顶层、`item::` 表里、表的表里。`<< ... >>`
    文本块的内容**原样**搬过去（那是值，缩进它会改掉值）。读不到、成环（a 引 b、b 引 a）、嵌套超过 16 层、
    `#` 后面没写路径，四种都是错误，而且错误信息里带着是**哪个文件的哪一行**要的它。片段要**带 `_` 前缀**
    （`_parts.ecfg`、`_ores/`）：内容包扫描时，名字以 `_` 开头的文件或目录**不是内容文件**——片段被自己读
    一遍、又被 include 一遍，同一份内容就会注册两次。片段还可以**自己声明**：`__not_main` 取三个值之一——
    `"skip"`（直接加载时**跳过**，不报错，重载也照样跳过）、`"true"`（直接加载时**报错**，只允许被 include）、
    `"false"`（与不写一样），两个布尔字面量 `true`/`false` 等价；别的值一律是错误，不会被猜成 `false`。引擎自带
    的三条加载路径（内容包扫描、模组宿主、沙盒重载）都按它跳过或拒绝，`EcfgDocument::main()` 让别的调用方也
    能问出文件自己说了什么。这个字段**属于文件**：被 include 时它不跟着内容走，所以包住它的主文件照常能加载
    （设计者 M2.18 的第三条："防止错误加载或重加载"）。
33. **层定义器的 `place_block`**（原话）："在层定义器中添加place_block字段，可以在指定位置放置具有指定属性的方块，格式为
    place_block:: / placement1:: / x:111... subobject:: / container:: / items:["aaa",100,"bbb",100]"（原文有换行与缩进）。
    于是：**一层可以在它自己说的位置上放一块指定的东西，并且一开始就装着指定的物品**。一条放置说四件事——**是什么**
    （`kind:"warehouse"` + `content:"stone"`，与 `scatter` 同一对字段）、**在哪个瓦片层**（`layer`，默认 0）、**在哪一格**
    （`x` 与 `y`，两个都要写：一格有两个坐标）、**装着什么**（`subobject:: container:: items:[名字,数量, …]`，名字是**物品**的
    名字、数量是正整数，写几个槽就是几个）。它在**地板之后、散点之前**落下——固定位置正是它的意义，而占住那一格之后
    散点就不会落在上面（与"一个格子一个瓦片层只放一个东西"同一条规则）。**"指定属性"今天只有容器一种子对象**
    （`subobject::` 是引擎的词，将来的机器输入侧、需求提交箱是同一层里的别的子对象）：别的名字直接报错，不会被忽略；
    读不到、装了注册表里没有的物品、容器装不下、格子在地图外，都会在**构建报告**里说清楚是哪一块、在哪一格。
34. **`building` 子对象与建造接口**（原话）："创建building子对象，包含对应地块的所需材料，建造时间，建筑分类（存储，
    加工，开采等，后续需要），提供建造相关的接口，包含can_place等方法在放置前判断对应的位置是否符合放着的条件，
    例如钻头必须放置在矿物上等"。于是：内容条目下可以写 `building:: materials:["stone",10,"chunk",2] time:5
    category:"extraction"`（材料是"名字, 数量"成对数组，与 `items` 同一套写法；时间是秒；分类今天有 storage /
    processing / extraction 三个，别的名字**报错**，将来要加新的就加名字）。地块通过 `SceneTile::building()`
    回答自己是不是建筑、要什么、多久、干什么用。**放置前的判断是 `MineLayer::can_place(placed, &why)`**：位置在
    不在图上、瓦片层有没有、那一格是不是空的、以及内容自己的条件——**钻头必须站在矿上**（同一格更低瓦片层里有
    矿），层构建时对钻头强制这一条，不合就进构建报告。
35. **定义属性与存档属性（享元）**（原话）："我们需要让地块和子对象的属性分为定义属性(例如1个仓库容量是100这一类
    固定属性)和存档属性（例如一个仓库里面有什么）并让他们区分起来，其中定义属性不可以在层设置中覆盖，地图上的所有
    同种地块读取同一份定义属性，参考享元设计"。于是：**一份内容条目 = 一份定义**（`TileDefinition`：容量、掉头、
    图片、挖掘力、硬度、掉落、`building`），它由 `ContentDefinitions` 持有、**活过所有从它建出来的层**；**一个地块
    实例 = 只存自己的状态**（容器里有什么、钻头挖到哪、脏不脏、朝向是哪次骰子给的）。地块通过 `SceneTile::definition()`
    拿到那一份共享记录，固定属性**都从它读**——所以一万块地板是一万个小对象加**一份**定义，不是一万份拷贝。
    **层设置只能写存档属性**：`place_block` 的 `subobject:: container::` 只认 `items`，写 `capacity:` 直接报错，
    定义属性改不动。

以上三十五条是当前唯一的内容性输入。除此之外的一切内容均由设计者后续提供（见 §7）。

## 2. 由已确认需求推导出的工程约束

这些是**技术结论**，不涉及具体内容：

* **"层"是一等概念**：层要有独立的地图实例、独立的资源/结构/需求集合，以及"层间推进"的
  状态机（当前层 → 需求全部完成 → 解锁下一层）。
* **"需求"是一等概念**：需求 = 目标（原料或产物）+ 数量 + 提交方式；完成判定必须在服务端权威
  执行，并且状态可被客户端观测（HUD / 终端面板）。
* **内容必须数据驱动**：既然内容由设计者定义，代码里**不能**出现资源枚举、结构枚举、配方表或
  建筑清单。层、资源、结构、需求、配方、建筑都以数据描述，代码只提供加载与执行。
* **内容（定义与逻辑）要能从外部加载**：本体只做核心逻辑，内容以**模组包**形式提供——一个目录、一份
  清单、若干内容文件，外加可选的 **C++ 模块**（共享库 + 版本化的 C ABI）。一个模组坏了只影响它自己：
  报告、跳过、游戏继续跑。见 `docs/MODS.md`。
* **内容必须可观察**：内容由设计者写、且会反复修改，"改一个文件立刻看到结果"必须是工具的一部分，
  而不是每次重启游戏。为此提供**单层沙盒**调试模式（`docs/SANDBOX.md`）：只渲染一层、没有需求与
  推进，面板列出数据注册出的内容与 id，改完文件按 F5 重载，已放置的格子按**名字**重新定位。
* **程序生成**：无尽模式的层内容必须由 `(seed, 层号)` 唯一决定，同种子完全可复现
  （可复现是联机与问题复现的前提）。
* **多边形是美术风格，资源仍是图片**（§1.10）：贴图是"多边形风格"的**图片**（低多边形、平色块、
  硬边），引擎**照常使用图片资源**——位图文件随内容包提供，引擎加载成纹理后按格子绘制。
  引擎**不做矢量多边形渲染**：多边形感来自美术，不来自几何；现有的 `SpriteBatch`（带贴图的四边形）
  就是画它的方式。
  由此定下的工程约束：内容包要能带**图片文件**，内容条目用相对路径引用（`image:"art/wall.png"`），
  引擎负责解析路径、校验文件存在、加载纹理（Ore 已有 PNG 解码：`ore::Image::load_png`）。
  `[已实现]` 加载时解析并校验 `image` 字段（存在性 + PNG），沙盒已经用**真实贴图**画格子与面板色块
  （截图见 `docs/MODS.md`）。**一份内容一张纹理、不进图集**（§1.18）：每份带图的内容单独一张纹理，
  按原样上传，绘制时按内容分组（一个批次绑定一张纹理）。世界渲染在 M2 里走同一条路。
* **没有玩家角色**（§1.11）：不存在"角色"这个实体——没有角色贴图、没有角色碰撞体、没有角色移动。
  输入是**相机与指针**：平移/缩放视角、指向格子、选择并下达动作。多人时每个玩家各有一份视角，
  作用在**同一张图**上（是否协作/竞争仍未定，见下条）。这也意味着"出生点"这类字段不属于握手与地图数据，
  而"玩家位置"不需要进快照——**要同步的是世界状态与各自的视角**。
* **地图是“上百格见方”的量级，相机与指针是唯一输入**（§1.11）：玩法要在几百×几百格的图上跑，
  所以存储、查询与绘制都**不能随地图面积线性变慢**：
  * 存储：框架的 `TileMap` 分块（32×32）惰性分配；游戏自己的地图格 `mine::ContentGrid` **每格 4 字节**
    （内容 id + kind + “内容已消失”标志打包进 32 位），**按层惰性分配**，已放置计数是计数器而不是遍历——
    512×512 一层 1 MiB，1024×1024×8 层全写满 32 MiB。`[已实现]`
  * 查询/绘制：`t2d::Camera2D::visible_cells()` 给出视口覆盖的格子范围，渲染只走这一段；
    缩放很小时按“每 N 格一个四边形”采样绘制（见 `docs/SANDBOX.md` §7）。`[已实现]`
  * 相机：平移、以指针为锚点缩放、复位、边界限制（`clamp_to`：视图停在图边，图小于视口时居中）。`[已实现]`
  * 指针坐标：**平台层就把指针换算成帧缓冲像素**（`ore::PixelScale`：帧缓冲尺寸 / 窗口内容尺寸，
    逐轴），命中测试、绘制与相机锚点因此是同一套坐标；缩放显示器（1.6667 倍的 GNOME/Wayland 会话）
    上不做这一步，指针会整体偏向左上、永远到不了界面右下角。`[已实现]`
  * 每帧动态数据（顶点）从 upload ring 的一段里分配，**段满则整批丢弃**，所以一屏四边形多的界面
    必须把 `AppConfig::upload_segment_size` 调大（mine 用 4 MiB）。`[已实现]`
* **世界是地块的集合，格子是它的索引**（§1.12、§1.13）：一层矿场 = 一张地图格 + 一堆地块 + 一副骰子，
  三者都由 `mine/world.h` 的 `MineLayer` 持有，`MineWorld` 持有"哪一层正在被玩"。**地块与地图格都要有，
  因为它们回答的问题不同**：地图格（`ContentGrid`，每格 4 字节）回答"这一格是哪条内容"——存档、路由查询、
  剔除都走它；地块回答"这是什么东西"——占地（3×3 是一个地块而不是九个格）、节奏、朝向。**只有被进入的那一层在
  内存里**（层数可以很多），而生成器只看得到 `(seed, 层号)`，所以再进来一次拿回的是同一个矿场。
  * **查询与绘制不随地图面积变慢**：地块按 32×32 的块建索引（与框架 `TileMap` 同一套分块），
    一个 3×3 会登记进它碰到的每个块，**一次查询里每个地块只被访问一次**（戳记去重）；绘制、放置检查、
    指针命中的成本因此是"屏幕上有什么"。
  * **代价写在明处**：地块是 C++ 对象（约 56 字节），地图格是 4 字节。**一层里每一格都是一个地块的图，
    存储是打包格子的十倍以上**——设计者的层规则（§7.3、§7.4）决定一层有多少地块，这条数字是给那时候用的。
  * **两条推进路径**（§1.13）：`refresh()` 走过全部地块、只为脏的付钱；`tick(dt)` 只走"会跑的"那些
    （层在创建地块时就分好了列表，不在运行时判类型）。两条路径每帧各一次，做了什么由世界视图的 HUD 报出来。
  * **世界还有第二半：实体**（§1.24）：地块是"占着格子的固定物"，**实体**是"不在格子上、会动的东西"。
    它有一个**位置**（浮点，**不与瓦片地图对齐**——3.5、2.25 就是一个位置，没有任何东西会把它对齐到格子上），
    能**移动**、能**交互**，并且**默认每 tick 被更新**：声明一个更新间隔就按间隔跑，声明"不自动更新"就一次
    也不跑（那就由别的东西驱动它）。两者回答的问题不同，所以**实体不继承地块**：地块回答"哪一格是什么"
    （格子 + 占地 + 朝向），实体回答"什么东西在哪一点"（位置 + 移动）。一层里**所有实体编入一张四叉树**
    （`mine/quadtree.h`），所以"这个位置一定范围内有哪些实体"是**答案的代价**，不是"这一层有多少东西"的
    代价——实测（release，10000 个实体铺在 1000×1000 的层里）一次半径 20 的查询走 21 个节点、只测
    **31 个条目**，而线性遍历要测 10000 个。
  * **生成器接口固定为 `(seed, 层号) -> LayerSpec`**：`LayerSpec` = 地图形状 + 要放的内容（kind、名字、
    瓦片层、锚点、占地）。故事模式回设计者的数据，无尽模式由种子推出来，**两者产出同一种结构**，
    下游（渲染、需求、推进）不需要区分模式。**故事模式的层规则已经是数据**（`layer::` 的
  `size::` 与 `floor::`，见 §4 与 `docs/MODS.md` §0），所以故事模式放的正是设计者写的东西；
  **还没有规则的地方**（无尽模式、以及故事里"每层有哪些资源/结构"）生成器什么都不放：
  空层也是层——能进、能走、能查、能画。`[已实现]`
* **内容逻辑有它自己的命名空间**（§1.12、§1.13）：定义是数据（`.ecfg` 表 + 注册表），**逻辑是 C++**，
  住在 `mine::types`（`docs/TYPES.md`）。这个命名空间是两半之间的契约：数据说"有什么"，类型说
  "它怎么运转"。**里面不出现任何内容名字**——没有资源、结构、机器、配方被写进代码。
  由此定下的工程约束：
  * **地块（`types/tile.h`）是"占据格子的固定物体"的基类**：地板、矿物、机器都是它。它带
    **kind + id**（与地图格、存档同一套身份：名字永远来自注册表，地块不存名字），
    **占地矩形**（左上角为锚点；`covers`/`cell_count`/`within`/`overlaps`），以及"内容是否还在"
    （内容消失时保留 id 与位置，回来时按名字修好）。**2×2、3×3、2×3 不是特例，而是同一个矩形**，
    所以"一个结构跨格怎么办"在类型层不是分支。
  * **地块分两类，而且是一棵继承树**（§1.14）：`Tile` → `SceneTile` → `EntityTile`。场景地块
    **没有每帧路径**（脏标记 + `refresh()`，调用方只为"改过的东西"付钱）；**实体地块是场景地块**
    （世界变化时同样按需刷新）**再加自己的节奏**（`period_seconds()`：0 = 每 tick；`advance(dt)` 到点才运行）。
    因为实体地块**是**场景地块，"要不要 tick"不能靠运行时判类型：**层在创建时就把要 tick 的地块放进
    自己的列表**，刷新那一遍走过全部地块、只为脏的付钱，tick 那一遍只走机器。这就是省下来的东西。
  * **渲染朝向是地块的属性**（§1.14）：基类带 `random_reverse`（内容数据说"这块内容可以掉头"）与
    `mirrored()`（结果）。**只在地图初始化时掷一次**，用**层自己的 `t2d::Rng`**（种子来自世界 seed）
    决定 50% 左右翻转，之后渲染每帧只读结果；**开关为假的地块不消耗随机数**（改一块内容不会把后面
    地块的骰子整体挪位）；**它只关于渲染**——地块做什么从不被镜像。手工指定用 `set_mirrored()`。
  * **节奏按时间而不是按 tick 计数**：`advance()` 拿到的是这一帧的秒数，余数留下（一秒的周期不漂移）；
    **一帧长于一个周期时只运行一次**，并把**整段时间**交给 `on_update(elapsed)`——地块不能补跑错过的
    tick，否则"矿场产出多少"会取决于帧是怎么掉的；这段时间怎么记账是内容的事。
* **地板是一类内容，也是一个标记**（§1.16）：`ContentKind::Floor`（**追加在类别表末尾**——类别值
  被打进每个地图格与每份存档，插在中间等于给后面的内容重新编号）与 `mine::types::Floor`
  （`SceneTile` 的子类，只多一个 `is_floor()` 标记）。**"是不是地板"是东西的种类，不是数据里的开关**：
  机器放下之前问脚下的格子、寻路迈步之前问前面的格子，都不需要知道任何一块地板的名字。
  沙盒把 `floor` 与 `ore` 也算作"占格子"的类别，所以设计者能直接把泥地与石头铺出来看。
* **矿物是一类内容，也是一个标记**（§1.19）：`ContentKind::Ore`（同样**追加在类别表末尾**）与
  `mine::types::SingleOre`（`SceneTile` 的子类，只多一个 `is_ore()` 标记：一格一块、可以挖出来的
  东西——`ore::` 表声明）。**散点生成器**是层创建器的一种（`layer::` 的 `scatter::`）：在指定瓦片层上
  按**平均密度**撒指定的内容，**最小/最大生成数量**夹住结果，**地板限制**决定哪些格子可用；
  **数量由规则定、位置由这一层的骰子定**（同一个种子同一张图，不同种子同一个矿场的不同布局）。
* **美术资源一块内容一张图**（§1.18）：引擎**不为内容建图集**——每份带图的内容单独一张纹理，按原样上传
  （尺寸随意，一格通常 128/256 像素；不缩放也不拒绝）。代价写在明处：**一次绘制绑定一张纹理**，所以
  屏幕上出现几种图就是几个批次（沙盒一屏是个位数；M2 的世界渲染按内容分组绘制，瓶颈出现时再谈纹理数组）。
  命名不限，**官方内容用蛇形命名**。
* **引擎会读的字段是两个**（§1.15）：`image`（贴图，路径相对**声明它的那个文件**）与
  `random_reverse`（是否允许地图初始化时左右翻转渲染）。**读不懂就报告**：`random_reverse:1` 是数据错误，
  不是"悄悄当成假"。其余字段全部是设计者的，引擎不看。本体内容（`games/mine/content/`）与内容包、
  模组的内容文件走同一套规则。
* **一张地图要有多个瓦片层**：地面、矿脉、结构、物流这些东西要能**分开描述、分开查询、分开渲染**——
  一层放一样，绘制自下而上叠起来；碰撞查询按"层掩码"（`LayerMask`）走，**哪一层挡路由游戏数据决定**，
  引擎不预设"第 0 层是地面"这种含义。层数上限 32，每层各自分块存储，没写过的层只占块头。
* **俯视语义**：游戏要的是平面俯视、格子对齐、**无重力**，与横版平台跳跃无关；框架里曾经用于验证的
  横版演示（平台跳跃世界、它的快照/预测与美术）已按设计者的判断**删除**——它不是本项目内容，
  留着还会把尚未确定的联机与模拟设计往那个形状上带。游戏自己的俯视模拟层在 M2 里建，
  复用框架的 tilemap、渲染、传输层（`ILink`/共享内存/KCP）与协议框架。
* **联机形态未定**：框架已具备半分离通路（单机=共享内存、联机=KCP、专用服务器无图形），
  游戏层预留接入点，但**是否支持联机、几人、协作还是竞争，由设计者决定**。已确定的部分：既然没有
  玩家角色、所有人都是上帝视角（§1.11），那么"玩家"在数据上是一份**视角 + 选择**，不是地图上的实体。

## 3. 视角与操作（工程约束）

* `[M2]` 平面 2D 俯视、格子对齐、正交投影、**无重力**。
* `[M2]` **没有玩家角色**（§1.11）：输入不驱动任何化身，而是驱动**相机与指针**——
  * 相机：平移（方向键 / 拖拽）、缩放（滚轮）、复位；视角是每个玩家自己的一份；
  * 指针：指向格子（悬停即选中）、框选、对选中目标下达动作；
  * 动作表（挖掘、放置、取放、使用设施…）属于内容，由设计者给出清单后实现（§7.14），
    实现上必须支持键位重绑定与动作表可配置。
* `[M2]` 因此**不存在"角色与格子碰撞"这一层**：碰撞只服务于结构、物流与需求判定
  （哪一层挡路由层掩码决定）。`[已实现]` 相机的边界限制：`t2d::Camera2D::clamp_to()`（视图停在图边，
  图小于视口时居中），以及 `fit()` 一帧把整张图框进视口。`[已实现]` **缩放的上下限是设计者给的**
  （§1.30）：世界视图只能把一格画成 **40–100 像素**（`mine/view_limits.h`），于是 `fit()` 也只能到
  范围允许的地方——100×100 的层在 1280×720 的窗口里"整图入框"要约 12 像素/格，取景因此停在 40。
* 键位分工（工程建议，非内容）：相机一组键；指针/选择一组键；界面一组键；快捷键栏。
* `[已实现]` **世界视图**（会话界面按 Enter，或 `--world-view 1`）：进入矿场的一层，按游戏的方式画它
  （所有瓦片层自下而上、每个地块画满自己的占地、按 `mirrored` 左右翻转、没有网格线与标签），
  输入只有相机与指针，底部两行 HUD 说出这一层是什么、指针指着哪个地块、以及两条推进路径这一帧做了什么。
  指针现在能做两件事：**按住左键拖动掉落物**（§1.25），以及**双击选中带容器的地块**——它的内容显示在
  界面最上方居中（§1.31）。
  `[ ]` 走进上一层/下一层（只有被进入的那层在内存里，同一 `(seed, 层号)` 再进来是同一个矿场），
  `C` 复位视角，`F5` 重载内容并重建这一层，`F6` 内容列表，`Esc` 回会话界面。
  `--layer-fill bands|scatter` 是**调试填充**：它不点名任何内容，只把注册表里的东西铺出来——
  是"注册表长什么样"的视图，不是矿场的规则（与沙盒的 `--fill` 同一条约定）。
  `--layer-drops 1` 是**掉落物的调试填充**：把注册表里 `drop::` 的每一条铺一个在层里（同样不点名内容），
  好在"按数据放掉落物"的规则出现之前先看见它们、拖动它们。
  指针能"做"什么仍然等动作表（§7.14）——**第一个动作已经给了**（§1.25）：**按住左键拖动掉落物**；
  其余动作（选择、框选、放置、取放、下达、取消……）仍在等。
  `[已实现]` **左上角的层数**（§1.20）：`层1/2`——**从 1 开始数**（玩家数的第一层就是第 1 层），
  斜杠后面是故事描述的层数；故事没有描述这一层（走到故事之外）或是无尽模式时只写当前层
  （没有总数可说，不编一个）。**模式说了算**（`layer_depth_for(模式, 规则, 层号)`，
  `mine/layer_rules.h`）：只有故事有总数可数，所以无尽模式不会因为本体内容描述了第 1 层就把自己说成
  "1/1 层矿场"。它画在**图层之上**（与底部状态栏同一条规则：地图不能把玩家自己的状态画掉）。
  底部那行仍然是**引擎的**编号（从 0 开始，与 `--mine-layer` 一致）——两个读者，两套编号。
* 沙盒（`docs/SANDBOX.md`）现在就是这套操作的样子：光标 + 相机 + 指针动作，没有角色；
  它的**试玩**（按 `P`，§9 of `docs/SANDBOX.md`）把这套操作单独拿出来跑一遍——同一层、按游戏的画法画、
  输入只有相机与指针，是 M2 世界视图的第一个使用者。

## 4. 分层世界（工程约束）

* `[M2]` 层由**数据描述**，字段至少包含：层号、层名、该层资源集合、该层结构集合、该层需求集合。
  具体字段与含义待设计者确认（§7）。
* `[M2]` 每层一张独立地图实例；进入某层时才生成/加载（层数可以很多）。
* `[M1]` 层里的东西是**地块**（§1.12）：占据格子的固定物体，可以只占一格，也可以占 2×2、3×3、2×3。
  地块属于**某一层**（`Tile::layer()`），重叠判断因此只在同层之间成立——地板与站在它上面的机器
  是两层上的两个地块，不是冲突。类型见 `mine/types/tile.h`，说明见 `docs/TYPES.md`。
* `[M2]` 层间通道：由数据描述（通道类型与解锁条件），当前唯一确认的解锁条件是"本层需求全部完成"。
* `[已实现]` 生成器接口固定为 `generate_layer(seed, index) -> LayerSpec`（`mine/world.h` 的 `LayerGenerator`）：
  * 故事模式：返回设计者提供的数据（预设流程）。
  * 无尽模式：由 `(seed, index)` 确定性生成。
  两者产出同一种数据结构，因此下游代码（渲染、需求、推进）不需要区分模式。
* `[已实现]` **故事模式的层规则就是数据**（`mine/layer_rules.h`）：`layer::` 下每个条目是一层，
  **写的顺序就是矿场的顺序**——第一个是第 0 层，第二个是第 1 层……与注册表发号同序，所以第 n 层的内容
  id 是 n+1，存档按名字永远对得上。一层的**创建器按固定顺序跑**（地板先铺、散点后撒），引擎读三张表
  （`docs/MODS.md` §0）：
  * `size::`：`width` / `height`（1..4096 格）、`tile_layers`（1..32）；不写的字段用会话/命令行的尺寸。
  * `floor::`：**地板创建器**——`layer` 选瓦片层（默认 0），规则 `full_flash:"<地板名>"` 把这一层的
    **每个格子**都设成那个地板（一格一个地块：每格因此都能单独换，`random_reverse` 也才有意义——
    一张覆盖全图的地块只有一个翻转决定）。
  * `scatter::`：**散点生成器**，一个条目一个——在指定瓦片层上撒指定的东西（`kind` + `content`），
    四个属性是**最小/最大生成数量、平均密度、地板限制**（外加它撒在哪一层）。可用格子 = 在图内 +
    这一层还没有东西 + 满足地板限制；数量在 `density × 可用格子数` 附近波动再被 min/max 夹住，
    **可用格子不够时地图赢**（限制是规则、最小值是愿望），差多少会**说出来**（`LayerSpec::problems`
    → 建层报告 → 画面）。落点来自这一层的骰子（`layer_seed(种子, 层号)`）：数量由规则定、位置由骰子定。
  条目下**其它字段是设计者的**（`name`、`resources`、以后的 `structures` / `demands`），引擎不解释；
  `size::` / `floor::` / `scatter::` 里的字段**是引擎的**，写错名字**指名报告**而不是忽略。名字注册表里
  没有时，层照建、每个格子被拒一次，但**只报一条原因**，画面中央写明原因。
  实测（解析 → 规则 → 生成器 → 建层）：48×32 的 `full_flash` = 1536 个地块 / 769 个翻转 / 0.7 ms；
  200×200 = 40000 个地块 / 23.6 ms；512×512 = 262144 个地块 / 154.6 ms。
* `[待设计者]` 层规则里**还没有的**：§7.3 的"每层生成哪些资源/结构"、§7.8 的故事流程（层数、每层目标、
  剧情文本）、§7.10 的数值。（§1.21 给了第一份：1 层、100×100、石头 20–35；其余仍在等。）无尽模式仍由 `(seed, 层号)` 推（§7.9 未定），所以它进的是空层；两个
  **调试生成器**（`debug_band_generator` / `debug_scatter_generator`：把注册表里的内容铺出来，
  不点名任何内容）仍在，用于"内容还没进层规则时先看看它长什么样"。
* `[已实现]` **物品类与 `item::` 定义器**（§1.22）：`mine::types::Item`（`types/item.h`）是"不在图上的
  内容"——机器产出、配方进出、需求点名、玩家携带的都是它；身份与地块同一套（**类别 + 注册表发出去的
  id**，名字永远在注册表里），引擎为它读的字段只有 `image`（`random_reverse` 是**地块**的字段）。
  数据侧 `item::` 表 → `read_item_definition()` / `item_definitions()` / `make_item()`
  （`types/item_definition.h`），加载时读一遍并**留下来**（`ContentDefinitions::find_item()`）。
  **本体内容里的第一件物品就是石头**（§1.23）：`content/items.ecfg` 的 `item:: stone::` 与贴图
  `content/art/item_stone.png`——它与矿物 `stone` 同名而不冲突（名字按种类发号），加载时被注册、定义被
  留下、贴图被解码成它自己的一张纹理；**其余物品仍然是设计者的**（§7.2），代码与数据都不编。
* `[已实现]` **实体类与它的四叉树**（§1.24）：`mine::types::Entity`（`types/entity.h`）是**不在格子上**
  的东西——它有一个**位置**（浮点，不与瓦片地图对齐）、能移动、能被要求交互，并且**默认每 tick 被更新**：
  声明更新间隔就按间隔跑，声明"不自动更新"就一次也不跑（由别的东西驱动它）。节奏与地块**共用一条规则**
  （`types/update_cadence.h`）：一帧比一个周期长时**只跑一次**，把整段时间交给它，不重放错过的 tick——
  否则一次卡顿就会改变矿场产出什么。实体**不继承地块**（地块是格子，实体是一个点），两者共享的是身份
  （类别 + id + 注册表给的名字）。一层里的实体由 `MineLayer` 持有并**编入一张四叉树**（`mine/quadtree.h`），
  `entities_within(点, 半径)` 回答"这附近有什么"，结果按**出生顺序**给出（同一个问题两次得到同一个答案）；
  移动与销毁都经过层，所以索引不会因为谁忘了说而失效（移动是实体自己告诉层的：它知道自己属于哪一层）。
  **还没有内容生成实体**（§7.7 等设计者）：现在能造出实体的只有 C++——本体或代码表模组。
* `[已实现]` **掉落物**（§1.25）：`mine::types::Drop`（`types/drop.h`）是**实体的一种**，它把两件事定下来——
  **层不更新它**（躺在那儿不会自己变化），并且**指针可以拖它**（`draggable()` 为真，`PointerDrag` 负责拖）。
  数据侧 `drop::` 表 → `read_drop_definition()` / `drop_definitions()` / `make_drop()`
  （`types/drop_definition.h`），引擎为它读的字段只有 `image`（它躺在地上长什么样）。
  它和地块一样有身份（类别 + 注册表发出去的 id + 名字），和实体一样有自由位置与四叉树——世界里它画成
  **一格大、以位置为中心**的图，所以躺在四格之间时就是压在四格上（这正是"位置不是格子"的样子）。
  `--layer-drops 1` 是它的调试填充（一层里每个 `drop::` 条目铺一个）；**还没有数据说"哪里该有掉落物"**，
  所以游戏本体内容里一个掉落物都没有——等的正是 §7.2/§7.7。
* `[已实现]` **钻头**（§1.26）：`mine::types::Drill`（`types/drill.h`）是**实体地块**（`EntityTile`），
  它站在矿**上面**——矿在它下面的瓦片层，因为一个格子每层只放一个地块（§1.12）。数据侧：
  `drill::` 表给 `dig_power`（挖掘能力），`ore::` 表给 `hardness`（硬度）与 `drop`（挖出来是哪条掉落物）。
  **周期 = hardness / dig_power**；到点就往四个方向轮流丢一个掉落物实体，一格远（§1.25 的掉落物，所以能拖）。
  这两件事都在**建层时**定下来：层手里同时有注册表（名字 → id）与定义（设计者的数字），于是"脚下没矿"
  "矿没说自己多硬""矿没说自己掉什么""钻头没说自己多能挖"都是**建层时就说出来的拒绝**，而不是一台永远
  默默不动的机器。一帧比一个周期长时，它按这一帧覆盖的时间**丢出相应个数**（§1.13 的节奏规则：
  一次卡顿不改变矿场产出什么）。
  实测（夹具层 24×16、3 个瓦片层、一条 hardness 2.0 的矿脉、一台 dig_power 1.0 的钻头）：
  `world: the drill 'rig' at 18,3 mines ore 'vein' (hardness 2.00 / power 1.00 = 2.00s per drop of 'chunk')`，
  跑起来之后钻头四周躺着它丢出来的掉落物（截图见交付状态（十））。
  **矿物不会被挖完**：一条矿脉有多少、挖完之后怎么办是设计者的（§7.3/§7.10）——引擎现在只按时间出料。
  `--layer-drills 1` 是它的调试填充：把 `drill::` 的每一条放在一个**有矿**的格子上。
* `[已实现]` **仓库**（§1.27）：`mine::types::Warehouse`（`types/warehouse.h`）是**场景地块**（`SceneTile`：
  不跑、不自动更新——它不是"会跑的功能地块"，而是**有人对它做什么的时候才发生什么**）。它由三个**子对象**组成，
  每个都是一件能单独用的东西：
  * `container`（`types/container.h`）：容量、里面有什么、按到达顺序列出；`add` / `take` **返回实际收下/给出
    多少**（满了就是 0，快满了就给能放下的那些），所以别的代码——机器、需求、存档、模组——可以直接跟它打交道；
  * `draginto`（`types/drag_into.h`）：接收拖过来的掉落物，**要么整件收下、要么什么都不变**（半件进一个满箱子
    是在撒谎）；
  * `click`（`types/click.h`）：接收点击——**点在它身上**就展开/收起面板，**点在别处**就收起（只有一个指针，
    所以只有一件东西是选中的）。
  数据侧 `warehouse::` 表读一个字段：`capacity`（本体自己的那一个是 §1.28 的 `warehouse:: stone::`，
  容量 100）。拖动松手时，掉落物**落在哪一格**就找那一格上的仓库
  （从最高瓦片层往下找，与画面上看到的一致）：进得去就进容器、地上那个随即消失（`PointerDrag::end()` 返回
  `Stored` / `Refused` / `Left`，HUD 把结果说出来——满了要在**错误色**里说）；点击则在地块**右下角**画出
  里面的东西，每一行是 **[贴图][本地化名称][数量]**（§1.28），标题是仓库自己的本地化名称
  （`STONE WAREHOUSE   1 / 100`、`石头仓库   1 / 100`），没写名字的内容就显示它的 id。实测（夹具层 20×12）：
  把掉落物从 (642,372) 拖到仓库 (375,482) → HUD `STORED drop #1 chunk`、地上那件的像素**全部消失**、容器里 1 件；
  再点一下仓库 → 面板出现在它的右下角（截图见交付状态（十一））。
* `[已实现]` **只有被进入的那一层在内存里**：`MineWorld::enter(层号)` 现建现用，换层就把上一层放掉；
  生成器只看得到 `(seed, 层号)`，所以**再进来一次拿回的是同一个矿场**（单测里两次生成的文本逐字节相同）。
  层与层之间的通道、解锁条件仍然等设计者（§7）。

## 5. 需求与提交（工程约束）

* `[M1]` 需求的数据结构：目标（物品/产物 id）+ 数量 + 提交方式 + 可选修饰（字段待定）。
  id 一律是**数据里的字符串/整数标识**，代码不解释其含义。
* `[M1]` **提交方式由设计者定义**。实现提供"可配置提交渠道"抽象：每种渠道声明
  * 接受哪些物品（过滤器）、
  * 如何接收（手动放入 / 由物流送入 / 由设施产出直接计入）、
  * 计数与扣除规则（累计、是否允许混入其它物品、是否要求连续供给）。
  具体有哪几种渠道、各自的规则，等设计者给出后再落地。
* `[M3]` 完成判定：渠道缓冲区内目标物品数量达到需求数量 → 扣除 → 需求标记完成；
  同一层的需求全部完成 → 解锁下一层。
* `[M3]` 需求状态（未开始 / 进行中 / 已完成 / 失败）必须出现在 HUD 与终端面板上。

## 6. 内容注册与存档 id 策略（工程约束）

内容由设计者以数据形式提供，且会随版本变化（增删、换序）。因此：

* **内容按名字注册**，运行时使用**数字 id**：每种 `ContentKind`（item / structure / machine /
  recipe / layer / channel / floor / ore）独立编号，从 1 开始，按注册顺序分配，保持紧凑（可存 varint）。
  kind 列表是工程定义而非内容；设计者引入新类别时**追加**它（§1.16 的地板、§1.19 的矿物都是这样来的），
  旧的存档表里没有这一类，读出来就是"这一类一条内容都没有"，不是读不懂。
* **存档只存数字 id**，并且**每份存档自带一张 name→id 表**（`ContentTable`，含 magic 与版本号）。
  只存数字是错的：版本一变，旧档里的 id 7 会被静默解释成另一个东西。
* **读档时按名字翻译**：`ContentRemap::build(存档表, 当前注册表)` 生成"存档 id → 当前 id"的
  双向映射。当前版本已不存在的内容进入 `missing()` 被**报告**，对应的 id 翻译成 0，
  由调用方决定这份存档还能不能继续（而不是悄悄复用数字）。
* **编码确定性**：同样的注册顺序 ⇒ 逐字节相同的表；不同顺序 ⇒ 不同的表（这正是表必须随存档走
  的原因）。同一份内容数据在客户端与服务端注册出的 id 完全一致，联机才可能对得上。
* **表编码**：magic + version + 逐 kind 的条目（id varint + name 字符串）。解码拒绝错误 magic、
  版本不符、截断、重复 id、重复名字、零 id、空名字、超长名字、尾随字节——读不懂就拒绝，
  绝不猜测。
* `[已实现]` `mine_core/registry.h`：`ContentRegistry`、`ContentTable`、`ContentRemap`；
  单测 `test_registry`（10 用例 / 128 断言，纯 CPU）。
* `[已实现]` **内容数据用 `.ecfg` 文件**（格式见仓库根的 `example.ecfg`，读取器 `t2d/core/ecfg.h`）。
  文件里以 kind 名（item / structure / …）开表，表内每个键就是一个内容名，键下面的字段由设计者
  定义、引擎不解释：
  ```
  item::
      <名称>::
          <设计者的字段>
  ```
  `mine_core/content_loader.h` 负责把名字灌进注册表；非 kind 的表会被**报告**而不是忽略（防拼写
  错误）。单测 `test_content_loader` 走通"配置文件 → 注册表 → 存档表 → 用变化后的注册表重新加载"。

### 内容的交付方式：纯 ecfg 内容包与模组包

内容不必编译进本体，有两种外部形式（`docs/MODS.md`），加载顺序固定为**本体内容 → 内容包 → 模组包**，
三者进同一个注册表，id 按注册顺序分配：

* **纯 ecfg 内容包**：**一个包就是一个目录**——若干 `.ecfg` 内容文件 + 它们的资源，可选一个
  `pack.ecfg`（顶层键 id / name / version / requires，与模组的 `mod.ecfg` 同一套）。没有清单、没有
  文件列表、没有代码。`--packs <dir>` 给一个目录：它本身是包就用它，否则它里面的每个包目录都是包；
  包内部按路径排序，包之间按目录名再按 `requires` 调整。**散落的 `.ecfg` 文件会被报告**（包是目录）。
* **不写参数时游戏自己找**（§1 之外的一条已确认需求）：`packs/` 目录**在可执行文件旁边**，
  把内容包与模组包丢进去就能跑，与启动时的工作目录无关；工作目录下的 `packs/` 是第二顺位（开发工作区）。
  同一个目录里 `*.ecfg` 是内容包、带 `mod.ecfg` 的子目录是模组包，**模组包目录不会被当成内容包扫描**
  （否则同一个名字会被注册两次）。两条都是缺省：目录不存在不报错，显式写出来的路径不存在会报错。
  细节见 `docs/MODS.md` §0。
* **模组包**：目录 + 清单 + 可选共享库，用于需要"跑点什么"的内容。

* 包 = 目录 + `mod.ecfg` 清单 + 若干内容文件 + 可选的共享库。清单里出现未知的键、缺 id、依赖缺失或
  成环、内容文件语法错、原生库缺失/ABI 不符/`on_load` 拒绝——一律**报告并跳过该包**。
* 三者进入**同一个注册表**，**本体内容先注册**：本体的 id 因此保持稳定，内容包与模组只能往后追加。
  同名内容**报冲突而不合并**（谁先注册谁保留，冲突记进报告）；内容包重定义本体内容时，本体赢。
* 原生模组编译时只需要 `mine/mod_api.h`（及其引用的类型头），**不链接本体的任何库**；跨过 ABI 的只有
  纯数据与函数指针，接口按"只追加 + `struct_size` + 版本号"的方式演进。
* `[已实现]` 单测 `test_module`（5 用例 / 33 断言）、`test_mod_package`（9 用例 / 104 断言）与
  `test_content_pack`（13 用例 / 198 断言，覆盖包头错误、重复 id、依赖缺失与成环、语法错、重定义本体内容、
  三来源顺序与重载一致性、本体内容自带贴图、引擎字段写错被报告），示例在 `games/mine/tests/{packs,mods}/`。

## 7. 需要设计者提供的内容清单（本清单就是"内容接口"）

| 2 | **资源与物品表** | 有哪些资源/产物、id 与**显示名**（界面上的名字写在字符串表里：`content.name.<种类>.<名字>` / `content.name.<名字>`，见 `docs/TEXT.md` 与 §1.28）、哪些属于"原料"哪些属于"产物"。**格式已落地**：`item::` 表 + 物品类（`mine::types::Item`）与它的定义器，引擎读 `image`（§1.22）。**第一件已经给了**（§1.23）：`item:: stone::`，贴图 `art/item_stone.png`。**掉落物的机制也落地了**（§1.25）：`drop::` 表 + 能被指针拖动的掉落物类——等的只是其余物品、哪些是原料哪些是产物、以及**什么东西会掉出什么** | 数据层、背包、需求 |

| 4 | **结构表** | 有哪些结构、每层生成什么、是否阻挡/危险。**矿物已经是自己的一类**（`ore::`，一格一块，散点生成器撒的就是它）——等的只是有哪些矿、在哪几层、多密。**第一块已经给了**（§1.21）：`ore:: stone::`，贴图 `art/ore_stone.png`。**矿也能说自己多硬、挖出来掉什么**（§1.26 的 `hardness` / `drop`）——等的只是这些数字 | 生成器、碰撞、渲染 |
| 5 | **需求的具体形式** | 提交方式有哪几种及各自规则；是否有数量曲线/修饰（限时、纯度…） | 需求系统 |
| 6 | **加工/配方链** | 配方（输入→输出）、耗时、是否需要设施 | 物流与加工 |
| 7 | **自动化要素清单** | 有哪些建筑/设备、物流形式（传送带？管道？机械臂？）、是否需要能源。**会动的东西的机制已落地**（§1.24）：实体类、四叉树、节奏都在——等的只是有哪些东西在动、动起来做什么。**第一台机器也落地了**（§1.26）：钻头会按"矿的硬度 ÷ 自己的能力"出料，丢出那条矿对应的掉落物。**第一个"存放"的东西也落地了**（§1.27）：仓库是场景地块，容器 + 拖入 + 点击看内容三件都在——等的只是还有哪些设备、物流怎么走 | 物流系统 |
| 8 | **故事模式流程** | 层数、每层的目标与顺序、是否有剧情文本。**层的存在与顺序已落地**：`layer::` 的书写顺序就是矿场顺序——等的只是层数与每层的目标。**第 1 层已经给了**（§1.21），所以故事现在有 1 层 | 数据（故事表） |
| 9 | **无尽模式生成规则** | 难度曲线、每层需求数量与数量级、随深度变化的东西 | 生成器 |
| 10 | **数值范围** | 层地图尺寸、数量级、期望的完成时长。**尺寸字段已落地**（`size:: width/height/tile_layers`，1..4096 / 1..32）——等的只是具体数字。**第一组已经给了**（§1.21）：100×100、石头 20–35 | 全局调参 |
| 11 | **联机形态** | 是否支持、人数、协作/竞争、断线处理 | 会话层 |
| 12 | **界面语言** | 是否需要中文界面（当前内置位图字体只有 ASCII 大写，中文需要换字体/字形表） | 界面 |
| 13 | ~~**多边形风格的图片规则**~~ **已确认**（§1.18）：一块内容一张图、不进大图集、尺寸随意（一格 128/256 像素）、官方内容蛇形命名 | **仍待补**：配色表、是否描边/渐变/半透明、动画帧、一个结构跨格怎么办、每个瓦片层用哪些图片 | 渲染、数据 |
| 14 | **指针动作清单** | 没有角色之后，玩家用指针能做哪些动作（选择、框选、放置、取放、下达、取消…），各自的鼠标键/键位，是否需要快捷键栏与"当前工具"概念。**前两个动作已经给了**：按住拖动物体（§1.25）、双击选中带容器的地块（§1.31） | 交互、输入 |

在收到 2/3/4/5 之前，任何层/资源/结构/需求的具体内容都不会被写进代码或数据文件——**设计者给一项，落地一项**
（§1.21 就是给的第一项：故事的第一层与石头）。

### M2 前置交付状态（二）：大图与相机（已落地）

玩法要在几百格见方的图上跑，而沙盒当时每格存一个名字（一个 `std::string` 加一次堆分配），一屏还要把可见格子
全部按格子画一遍。这一轮把两件事都换成能撑住大图的做法，并且都用真机数字验证：

* **相机进框架**：`t2d/core/camera2d.h`——视口、世界中心、缩放（像素/世界单位，格子游戏即像素/格）、
  `screen_of`/`world_of`（互为精确逆）、`zoom_at`（指针下的世界点不动）、`fit`（带边距框住一张图）、
  `clamp_to`（有界视角）、`visible_cells`（视口覆盖的半开格子范围，即剔除范围）。纯数学，无 GPU、无窗口。
  沙盒的相机整体换成它，行为不变（原有相机测试一条不改地通过），单测 `test_camera2d`（7 用例 / 1986 断言）。
* **地图格打包**：`mine::ContentGrid`——每格 32 位（20 位 id + 4 位 kind + 1 位“内容已消失”），
  按层惰性分配（没写过的层零占用），已放置计数 O(1)。格子不再存名字：名字来自注册表与每份存档自带的
  name→id 表（§6），所以重载仍然是“按名字重定位”，而且**消失的内容保留它的 id 并标记为缺失**，
  内容回来时能被名字修好。单测 `test_content_grid`（5 用例 / 105 断言）。
* **绘制与预算**：沙盒只走 `visible_cells()`；当可见格子数 × 层数超过四边形预算时，按“每 N 格一个四边形”
  采样绘制（`draw_step_for()`，N 由预算开方得出），低缩放下网格线与标签自动关闭。
* **框架修的两处**：退出顺序改为“先 `wait_idle()` 再 `on_shutdown()`”（此前无 `--screenshot` 的无头运行
  100% 触发 `VK_ERROR_DEVICE_LOST`）；`AppConfig::upload_segment_size` 让应用能给每帧动态数据留够空间
  （ring 段给不出空间时 sprite batch 会整批丢弃，屏幕全空）。

| 40×24 × 1 层 | 960 | 3 KiB | ~10 ms | 108.9 MB |
| 512×512 × 4 层 | 1.05M | 4096 KiB | ~11 ms | 108.9 MB |
| 1024×1024 × 8 层 | 8.4M | 32768 KiB | ~12 ms | 125.0 MB |

同一组运行在改造前是：512×512×4 用 134.5 MB / 2.25 s（20 帧），1024×1024×8 用 414.6 MB / 5.30 s——
存储从每格一个名字降到每格 4 字节，帧成本从“随地图面积”变成“随屏幕”。

### M2 交付状态（一）：世界（已落地）

里程碑 M2 要的是"进入某层并渲染出来"。这一轮交付的是**世界**：层、地块、两条推进路径、查询，
以及游戏自己的世界视图。**内容仍然由设计者给**——层里放什么（§7.3、§7.4）当时还没有，
所以生成器什么都不放，而"空层"是可用的：能进、能走、能查、能画。
（故事模式读设计者数据的层规则在**下面（二）**落地：`layer::` 的 `size::` 与 `floor::`。）

* **纯逻辑**：`mine/world.h`（`MineLayer` / `MineWorld` / `LayerSpec` / `LayerGenerator` /
  两个调试生成器），无 Ore 依赖，专用服务器将来直接用同一份。单测 `test_world`（**12 用例 / 130 断言**，
  毫秒级）：占地的每一格、同层重叠被拒、注册表里没有的内容被拒并说明、内容没有定义时仍然是一个地块、
  **同一 `(seed, 层号)` 两次生成逐字节相同**（`dump_text` 对比）、另一层是另一张图、
  只有"会跑的"进 tick 列表、刷新只为脏的付钱、块索引里跨块的 3×3 只被访问一次、
  掩码碰撞（含图外算挡路）、空层照常工作。
* **引擎会读的字段仍然只有两个**（§1.15）：`image` 与 `random_reverse`。管线本来就会读一遍好把
  写错的字段当场报出来，现在**把读到的定义留下来**（`ContentDefinitions`），建层时直接用——
  于是"这块内容能不能掉头"是从数据来的，不是代码里的开关。
* **界面**：世界视图（会话界面按 **Enter**，或 `--world-view 1`）——进入矿场的一层，按游戏的方式画：

  与沙盒的 `--fill` 同一条约定（"注册表长什么样"的视图，不是矿场的规则）。
  没有它时进的是**空层**，而空层在屏幕上明说自己是空的。

### M2 交付状态（二）：故事模式的层规则（已落地）

设计者的要求（原话）："添加一个故事模式层 ecfg 创建器，初次进入某个层时按照 ecfg 内的生成规则生成层，
首先需要添加大小设定和地板创建器，先添加一个 full_flash 字段，意为将所有地板设置为给定的地板类型。"

* **数据**：`layer::` 下一个条目一层，**书写顺序 = 矿场顺序**（与注册表发号同序：第 n 层的内容 id 是
  n+1）。`size::`（`width` / `height` 1..4096、`tile_layers` 1..32）与 `floor::`（`layer` +
  `full_flash:"<地板名>"`）是引擎读的两张表；条目下其余字段是设计者的（`name`、`resources`、
  以后的 `structures` / `demands`），引擎不解释——和别的内容条目同一条界线。见 `docs/MODS.md` §0。
* **引擎**：`mine/layer_rules.h`——`read_layer_rule()` / `layer_rules()` / `LayerRules`
  （同名先声明者保留，与注册表同一条规则）与 `story_layer_generator(rules, 世界形状)`。
  层规则由内容管线从**本体、内容包、模组包**三处一起读（与 `image` / `random_reverse` 同一条路），
  所以模组加一层和本体加一层没有区别。故事模式的生成器**不看种子**（预设就是每个世界都一样），
  进层时现建现用（§4）。
* **拒绝而不是猜**：`size:[40,24]`（数组）、`widht:40`（拼错）、`width:0`、`tile_layers:33`、
  `full_flash:3`（不是字符串）、`full_flash:""`、`floor:: layer:1` 而这一层只有 1 个瓦片层——
  全部**带文件名报告**，该层不进故事，同一个包的其它内容照常加载（列表上显示 PARTIAL）。
  地板名注册表里没有时**层照建**：每个格子被拒一次，但报告**只留一条原因**并计数
  （实测 16×12：`192 placement(s) refused in all, 1 reason(s) listed above`），画面中央写明原因。
* **画面**：一层是空的时，中间说明**为什么**——先是构建拒绝的原因（数据点了不存在的内容），
  再是"故事数据没有描述第 N 层"，最后才是调试填充的提示。
* **验证**：`test_layer_rules` **14 用例 / 330 断言**（读取器的每一条拒绝、故事顺序、尺寸覆盖世界形状、
  铺满每个格子、指定瓦片层、地板名缺失、后一条规则覆盖前一条、以及包 → 管线 → 世界端到端）。
  Tile2D 套件 25 → **26 个测试**（debug / release / asan / tsan 26/26、no-renderer 11/11、
  server-only 26/26）。真机（无头，1280×720）实测：
  `content: ... 2 story layer(s), 0 error(s)`、

### M2 交付状态（三）：矿物与散点生成器（已落地）

设计者的要求（§1.19 的原话）："添加一个 single_ore（单矿物）类继承场景地块，层创建器添加散点生成器，
以散点形式在指定 tile 层放置指定物体，包含最小生成数量，最大生成数量，平均密度，地板限制等属性。"

* **`SingleOre`**（`mine/types/single_ore.h`）：继承 `SceneTile`，只多一个 `is_ore()` 标记——和地板
  同一个形状的问题（"这里有没有东西可以挖"），所以调用方不用知道任何一块矿物的名字。**一格一块**：
  散点一格放一个，于是"哪一格有矿"和"哪块地块是那个矿"是同一个问题。它的类别是**新追加的
  `ContentKind::Ore`**（`ore::` 表）：追加不动旧值，而旧的存档表里没有这一段——
  `ContentTable::deserialize` 现在接受**更少的类别段**（那几类读出来就是空），多于本版本知道的类别仍然拒绝。
* **散点生成器**（`layer::` 的 `scatter::`，`mine/layer_rules.h`）：一个条目一个生成器，属性就是你要的
  那四个——`min` / `max`（最小/最大生成数量）、`density`（平均密度）、`floor`（地板限制），
  外加 `kind` / `content`（撒什么）与 `layer`（撒在哪个瓦片层）。
  * **可用格子** = 在图内 + 这一层还没有东西 + 满足地板限制；创建器**地板先铺、散点后撒**，所以
    "这一层已经有东西"包括地板，两个散点撒在同一层也不会互相压（后撒的避开先撒的）。
  * **数量**：每个可用格子以 `density` 为概率被选中（期望 `density × 可用格子数`），再夹到
    `[min, max]`，最后夹到可用格子数——**可用格子不够时地图赢**（限制是规则、最小值是愿望），
    差多少**说出来**：`LayerSpec::problems` 是这一轮新加的一条报告通道，生成器说得出它做不到什么，
    建层报告带着它，画面与日志都看得见。
  * **位置**：来自这一层的骰子（`layer_seed(种子, 层号)`）——数量由规则定、位置由骰子定。
  * 读不懂的字段**在读文件时就拒绝**：`kind` 不是类别、`kind:"item"`（不占格子）、没有 `density`、
    `density:5`、`min` > `max`、`floor` 写在没有地板创建器的层上、`layer` 超出这一层的瓦片层数。
* **顺手修掉一个只有真机截图才看得见的 bug**：世界视图原来把"没有贴图的内容"画在所有贴图**之前**，
  于是上一层没有图的矿被下一层地板的贴图盖住——撒了 13 块矿，画面上一块也看不见。现在**一层一层画**：
  每一层先画没有图的地块（名字派生的调试颜色）、再画这一层的贴图。同一趟还修掉另一件：HUD 与指针原来
  画在图层**之前**，放大到 48 像素/格时贴图会盖住状态栏（旧截图里就有）。现在是"底 → 层 → 界面"三趟
  （`draw_world_screen` / `draw_world_layer` / `draw_world_overlay`）。
* **验证**：`test_mine_types` 13 → **14 用例 / 187 断言**（`SingleOre` 是场景地块、两个标记互不冒充、
  `make_tile` 按类别造类、`item:: ore::` 是物品不是矿物）；`test_layer_rules` 14 → **22 用例 /
  712 断言**（散点的每一条拒绝、数量公式的三种情形、地板限制、两层不互相压、同种子同布局、超出瓦片层数
  说出来）。Tile2D 套件仍是 **26 个测试**（debug / release / asan / tsan / server-only 26/26、
  no-renderer 11/11）。真机（无头 1280×720，故事测试替身）：
  `world: layer 0 is 48x32 with 2 tile layer(s): 1549 plot(s)` = 1536 个地板 + **13 块矿**
  （`density:0.01`，min 6 / max 40）；放大到 48 像素/格时地板与矿各画各的、状态栏在最上面。
* **没有往本体内容里加任何东西**：仓库里唯一的矿物与散点数据仍是测试替身
  `games/mine/tests/data/story_content/`（本体 0 条层规则、0 条矿物，`test_content_pack` 钉住）。
  （**后来变了**：本体现在有 1 条层规则与 1 块矿物，`test_content_pack` 钉的正是它们，见（五）。）

### M2 交付状态（四）：左上角的层数（已落地）

设计者的要求（§1.20 的原话）："正式游戏中需要在左上角显示当前层数，格式为层1/层2"。

* **显示的就是这个格式**：`world.depth:"层{}/{}"`（英文 `LAYER {}/{}`、繁体 `層{}/{}`），
  **从 1 开始数**——玩家数的第一层是第 1 层，而引擎与 `--mine-layer` 数的是第 0 层，两套编号各自服务
  一个读者：左上角给玩家，底部那行给看日志的人。
* **斜杠后面是什么**：故事描述的层数（`LayerRules::size()`）。**没有总数的时候不编一个**：
  走到故事之外，或者无尽模式（层规则未定，§7.9），只写当前层（`world.depth.endless:"层{}"`）——
  一条"HUD 说 6/3"的规则比不显示总数更难解释。这条判断是纯逻辑，`layer_depth(规则, 层号)` 一个函数
  （`mine/layer_rules.h`），所以它测得到。
* **画在图层之上**：与底部状态栏同一条规则（M2.6 修的那条）——地图不能把玩家自己的状态画掉；
  它有自己的小面板，压在贴图上也能读。

### M2 交付状态（六）：物品类与 `item::` 定义器（已落地）

设计者的要求（§1.22 的原话）："添加物品类和物品ecfg注册器"。

* **物品类**（`mine::types::Item`，`types/item.h`）：**不在图上**的内容——机器产出、配方进出、需求点名、
  玩家携带的都是它。它没有地块、没有占地、没有层（"这个物品在哪一格"是**容器**的问题，而容器是设计者的
  数据，§7.10），所以它**不继承 `Tile`**：共用一个基类等于说两者是同一种东西，而地块有层与占地、物品两样
  都没有，一格能放地块、永远放不下物品。身份与地块同一套：**类别 + 注册表发出去的 id**，名字永远在注册表
  里（`Item::name(registry)`，内容没了就是 `#<id>`，与地块同一段文字）；`Item::valid(registry)` 答"它背后
  的内容还在不在"——重载把内容拿走后，物品保留自己的 id 并**说出来**，而不是悄悄变成占了这个数字的另一条
  内容。默认构造的是**空槽**：没有内容、没有贴图。
* **`item::` 定义器**（`types/item_definition.h`）：`read_item_definition()` 读一条、`item_definitions()`
  走一份 `.ecfg`、`make_item()` 把定义变成物品——与地块定义器（`types/tile_definition.h`）同一形状。
  引擎为物品读的字段只有一个：**`image`**（背包槽、配方、需求画的就是这张图）；`random_reverse` 是**地块**
  的字段（"这份内容画在地图上能不能掉头"），物品不在图上，所以写在那里的只是设计者字段，引擎不读也不报
  ——`docs/MODS.md` §0 的字段表据此改准了适用范围。表里写错 `image`（不是带引号的路径）**拒绝并说明**，
  与地块同一条规则；拿别的表（比如 `ore::`）的条目来读物品同样拒绝：条目写在哪个表里就是什么。
* **加载时读一遍并留下来**：`ContentDefinitions::find_item()` / `item_count()`，包与模组两条路都读
  （`content_pack.cpp` / `mod_package.cpp`），所以字段写错在**文件那里**就报，而不是等到有人要画它；
  启动那行现在报 `N plot definition(s), M item definition(s), ...`。查找刻意分成 `find_tile()` /
  `find_item()`：物品不是地块，按地块查它必须查不到，哪怕两者同名。
* **本体内容里一个物品都没有**：设计者还没说有哪些物品（§7.2），代码与数据都不编。这一条交付的是**机制**：
  `item::` 表从此有人读，读到的东西留得住、拿得到（`Item` 就是拿它的那一半）。

### M2 交付状态（七）：第一件物品——石头（已落地）

设计者的要求（§1.23 的原话）："创建物品石头 id=stone"。

* **本体内容里第一次有了物品**：`content/items.ecfg` 声明 `item:: stone::`，`content/art/item_stone.png`
  是设计者给的图（64×64，**逐字节**拷进本体包，与 `ore_stone.png` 同一个做法）。本体包的文件按路径排序
  加载（floors → items → layers → ores），所以它注册成 **`item #1 stone`**。
* **同名不是冲突**：矿物 `stone` 与物品 `stone` 同时存在——注册表**按种类发号**（`find(kind, name)`），

* **实测**（真机无头 1280×720）：`content: 1 base pack(s) with 4 and 3 image(s), 0 pack(s) with 0 and 0
  image(s), 0 mod(s) with 0 -> 4 registered, 2 plot definition(s), 1 item definition(s), 1 story layer(s),
  0 error(s)`、`images: 3 loaded, one texture per content entry (largest 256 px)`——**物品的贴图与地块走同一
  条路**（`load_content_images()` 遍历每一个解析成功的图片，没有按类别分支），所以它有自己的那张纹理。

### M2 交付状态（八）：实体与它的四叉树（已落地）

设计者的要求（§1.24 的原话）："添加实体类，位置不与瓦片地图对齐，可以移动，交互，默认每tick更新除非特别
声明更新间隔或不自动更新。为了保证性能，一个层运行时所有实体编入一个四叉树表便于快速检索一个位置一定范围
内的实体"。（这一条先写成"位置不固定与瓦片地图对齐"，随即更正为"位置**不**与瓦片地图对齐"——按更正后的
为准。）

* **实体不是地块**（`mine::types::Entity`，`types/entity.h`）：地块是**格子**（占着格、固定、有朝向），
  实体是**一个点**（不在格子上、会动），所以它**不继承 `Tile`**——继承等于说两者是同一种东西。
  两者共享的是身份：类别 + 注册表发出去的 id + 名字（内容没了就是 `#<id>`，与地块同一段文字）。
  位置是浮点的，**不与瓦片地图对齐**：3.5、2.25 就是一个位置，没有任何东西会把它对齐到格子上。
* **移动**：`set_position()` / `move()`。移动会**告诉它所在的那一层**（实体知道自己属于哪一层），
  层因此跟着更新索引——"一层里所有实体都在索引里"是**不变量**，不是一条要靠调用者记住的规矩。
* **交互**：`on_interact(Entity&)`（默认什么都不做，并且说出来），层提供 `interact(a, b)`——**两边都问**，
  有一边有反应就是"发生了一次交互"，而且两边都不必知道对方是什么类型。**交互具体是什么**仍然是设计者的
  （§7.14 指针动作）。
* **更新节奏**：默认**每 tick**；`set_period_seconds(s)` 声明间隔；`set_auto_update(false)` 声明
  "不要自动更新我"（它照旧在那里、照旧能移动与交互，只是由别的东西驱动）。节奏规则与地块**共用一份**
  （`types/update_cadence.h`，`EntityTile` 改成用它）：**一帧比一个周期长时只跑一次**，把整段时间交给它，
  不重放错过的 tick——一次卡顿不能改变矿场产出什么。
* **四叉树**（`mine/quadtree.h`）：一层里的实体编入一张四叉树，根是这一层的矩形，一个节点超过 **16** 个
  条目就分裂（最多 8 层）。`entities_within(点, 半径)` 返回**按出生顺序**排好的结果（同一个问题两次得到
  同一个答案），另有一个 visitor 版本不建列表。落在地图外的实体**留在根节点**：查询覆盖到它在哪里就找得到
  它，地图要不要拦住它是设计者的规则（§2），不是索引的事。索引只知道"位置 + 一个 payload"：它不认识实体，
  也不认识内容。
* **实测**（release，`test_entities` 自己打出来的数字；10000 个实体铺在 1000×1000 的层里）：
  一次**半径 20 的查询**走 **21 个节点**、只测 **31 个条目**——线性遍历要测 10000 个；
  **10000 个实体生成 0.79 ms**（边造边进索引）、**一次 tick 走过全部 10000 个 0.058 ms**、
  **1000 次半径 10 的查询 0.388 ms**（每次 **0.4 µs**，每次测 25.2 个条目、走 8 个节点，找到 3.1 个）。
* **层怎么改的**：`MineLayer` 持有实体（`adopt` / `spawn` / `destroy`）、它们的索引，以及
  `entities_within` / `for_each_entity_within` / `interact`。`tick()` 现在同时走**地块的节奏列表**与
  **实体**：地块多，所以继续用"创建时就分好的列表"；实体少，所以由层走过、每个自己决定——节奏是它自己的，
  而一张要跟着它改主意的列表是自找的麻烦。销毁是**立即出索引、帧末出存储**：正在遍历实体的回调手里的
  指针仍然有效。`MineWorld` 改成用 `unique_ptr` 持有那一层——**层里的东西指回层**，层一旦被搬走，
  那些指针就会指向一个不在那儿的层。
* **验证**：新增 `test_entities` **8 用例 / 129 断言**（自由位置不被对齐、默认每 tick / 间隔 / 不自动更新、
  余数不漂移、长帧只跑一次、两边都被问的交互、四叉树的插入 / 删除 / 移动 / 边界 / 同一位置的重复条目 /
  地图外的条目、半径查询的代价、层的索引跟着移动走、销毁立即出索引而帧末出存储、实体在自己的回合里能
  够到层（造一个、毁一个、问附近有什么并交互）、tick 顺序 = 出生顺序）。套件 **27 个测试**全绿
  （release / debug / asan / tsan / server-only 27/27、no-renderer 11/11、Ore 13/13）。
* **屏幕上一个像素都没动**：没有内容生成实体，也没有任何界面画实体——三张有代表性的文档截图
  （`world_story_en` / `sandbox_en` / `session_screen`）重渲染后**逐字节相同**（`compare -metric AE` = 0）。
* **顺带修掉一处会让人读到错数字的构建缺陷**：代码表的依赖里只有 `.cpp`——**改头文件不会重建表**，
  而表才是真正在跑的那个东西。这一次它当场咬人：`quadtree.h` 改了一个函数体之后表还是旧的
  （734 节 / 2329 符号 / 8981 重定位），强制重建才是 734 / 2330 / 8974。现在表的依赖里加上本体与引擎的
  头文件、生成的 `config.h`，以及它据以校验的 `engine.api`（`CONFIGURE_DEPENDS`，新加的头文件也会被带上）。
* **表与公开面**：本体表 706 → **734 节 / 2247 → 2330 符号 / 8756 → 8974 重定位**（release，
  1 146 806 → 1 178 601 B = 1.13 MiB；debug 5592 / 19023 / 24758 / 3.50 MiB），指纹不变
  （`bdcb9b070ab30e78`，头文件 77 → 80），align 分布
  `{1:121, 2:59, 4:6, 8:75, 16:406, 32:37, 64:30}`，向宿主索取的符号仍是 **160** 个（t2d 57 / ore 25 / 平台 78）。
* **还没有的东西**：① **没有 `entity::` 定义器**——设计者要的是"实体类"，不是"实体 ecfg 注册器"
  （§1.22 那次两样都要）；现在能造出实体的只有 C++：本体，或代码表模组。② **没有任何界面画实体**：
  世界里不画它，所以"实体长什么样"还没有答案。③ **交互是什么**仍然等 §7.14——机制在位，内容是设计者的。

### M2 交付状态（九）：掉落物与指针拖动（已落地）

设计者的要求（§1.25 的原话）："添加掉落物类和定义器，不自动更新，可以被鼠标拖动移动"。

* **掉落物是实体的一种**（`mine::types::Drop`，`types/drop.h`）：位置自由（不与瓦片地图对齐）、进四叉树、
  能被查到——实体那一半照旧（§1.24）——它把两件事定下来：**层不更新它**（`auto_update()` 天生为假：
  这是"它是什么"，不是条目里的字段），并且**指针可以拖它**（`draggable()` 为真；普通实体为假，
  与"我是不是地板"同一种问法）。
* **定义器**（`types/drop_definition.h`）：`drop::` 表 → `read_drop_definition()` / `drop_definitions()` /
  `make_drop()`，引擎为掉落物读的字段只有 `image`。为此**追加了 `ContentKind::Drop`**（追加在类别表末尾，
  旧存档表照旧读得出来：类别少一段就是"这一类一条内容都没有"），`content_kind_name` 给它 `"drop"`。
* **指针拖动**（`mine/pointer_drag.h`）：按下左键 → 取**最近的一个可拖的东西**（`kGrabRadius` = 0.75 格；
  并列时取小的 serial，所以同一次按下两次都拖同一个）→ 记住**抓取偏移**（拖起来不会跳到指针中心）→
  移动时跟着指针走、**夹在层的矩形内**（指针可以出图，被拖的东西不会）→ 松手放下。
  它只认世界坐标，不认像素与按键，所以整件事能在毫秒级的单测里跑完。
* **屏幕这一侧**：世界里掉落物画成**一格大、以位置为中心**的图（躺在四格之间时就是压在四格上——这正是
  "位置不是格子"的样子），画在所有地块之后；按住左键拖，HUD 第二行从格子描述变成
  `CELL 33,50   DRAGGING drop #1 scrap`（三语言）。`--layer-drops 1` 是调试填充：把 `drop::` 的每一条
  在层里铺一个（与 `--layer-fill` 同一条约定，不点名任何内容）。
* **实测（端到端：真机无头 1280×720，脚本隔着调试输入服务器移动鼠标与按键）**：把 32 像素/格的一屏里那颗
  掉落物从屏幕 `(635, 352)` 按住、移动 `+288, +96` 像素、松手——它自己的像素重心从 `(635.1, 352.1)` 走到
  `(923.2, 448.8)`，即**移动了 288.1 / 96.7 像素 = 9.00 / 3.02 格**（抓取偏移被完整保留：指针走多少，
  它就走多少）。按住时 HUD 是 `CELL 33,50   DRAGGING drop #1 scrap`，松手后是

### M2 交付状态（十）：钻头——实体地块，按"硬度 ÷ 能力"出料（已落地）

设计者的要求（§1.26 的原话）："添加一个钻头类，类型为实体地块，可以被放置在矿物上，按照定义器设定的挖掘能力/
矿物硬度计算时间，每段时间向外丢出一个矿物对应的掉落"。

* **钻头是实体地块**（`mine::types::Drill`，`types/drill.h`）：它继承 `EntityTile`（§1.13 的"会跑的功能地块"），
  占着一格、按节奏跑；跑起来做的事是**挖它脚下的矿**。矿在它**下面的瓦片层**——一个格子每层只放一个地块
  （§1.12），所以"钻头放在矿上"就是"钻头站在矿上面那一层"，落位检查本来就不拦这种叠法。
* **周期 = 矿物硬度 ÷ 挖掘能力**，两个数都是设计者的：`drill::` 表给 `dig_power`，`ore::` 表给 `hardness`
  与 `drop`（挖出来是哪条掉落物，§1.25 的 `drop::`）。为此**追加了 `ContentKind::Drill`**（追加在类别表末尾，
  旧存档表照旧读得出来），并给地块定义器加了三个按类别读的字段。
* **两件事都在建层时定下来**（`MineLayer::configure_drill`）：那是注册表（名字 → id）与定义（设计者的数字）
  同时在手的唯一时刻，所以"脚下没矿""矿没说自己多硬""矿没说自己掉什么""钻头没说自己多能挖"都是
  **建层报告里的拒绝**，而不是一台永远默默不动的机器——四种都在单测里钉住了。
* **到点往外丢一个**：四个方向轮流、一格远（所以钻头不会把自己埋在一个点上；出图时贴边），丢出来的是
  **掉落物实体**——上一轮那个能被指针拖走的东西。为此**地块第一次够得到世界**：`Tile::owner()` 是它所在的层，
  钻头用 `owner()->adopt(...)` 把掉落物放进层里。
* **一帧比一个周期长时按时间出料**：`on_update` 拿到的是这一帧覆盖的整段时间（§1.13 的节奏规则），
  所以一次卡顿丢掉三个周期就是三个掉落物——"一次卡顿不改变矿场产出什么"。

### M2 交付状态（十一）：仓库——容器、拖入、点击（已落地）

设计者的要求（§1.27 的原话）："添加仓库，类型为场景地块，通过定义器设定容量等参数，鼠标拖动掉落物到仓库上方即可
把掉落物加入到仓库中，点击在地块右下角显示包含内部物品信息的ui，仓库对象中包含子对象container用于存储物品信息
和处理存储功能并便于和其他代码交互，包含draginto子对象用于接收掉落物，包含click子对象接收点击信息"。

* **仓库是场景地块**（`mine::types::Warehouse`，`types/warehouse.h`）：`SceneTile` 的子类，**不跑、
  不自动更新**——它不是"会跑的功能地块"（那是 §1.13 的 `EntityTile`，钻头那种），而是**有人对它做什么的时候
  才发生什么**：一件被拖过来，或者被点一下。层的 tick 列表里因此没有它（单测钉住了 `ticking_count() == 0`、
  跑一百秒也返回 0）。
* **三个子对象，各管一件事，而且都能单独用**：
  * **`container`**（`types/container.h`）：容量、里面有什么、按**到达顺序**列出；`add` / `take`
    **返回实际收下/给出多少**——满了就是 0，快满了就给能放下的那些。它不认识仓库、也不认识掉落物：装的是
    "类别 + id + 数量"，与存档写的是同一对东西，所以机器、需求、存档、模组都能直接跟它打交道。
  * **`draginto`**（`types/drag_into.h`）：接收拖过来的掉落物。**要么整件收下、要么什么都不变**——
    半件进一个满箱子是在撒谎。这条规则当场抓出一个 bug：第一版先 `add` 再比较数量，于是"拒绝"的时候
    箱子已经被塞进了能塞的部分；现在先看空间再动手，单测钉住了"拒绝之后总数不变"。
  * **`click`**（`types/click.h`）：接收点击。**点在它身上**就展开/收起面板，**点在别处**就收起——
    只有一个指针，所以只有一件东西是选中的；它只记"开着没有"和"被点了几下"，面板画什么不归它管。
* **定义器给容量**：`warehouse::` 表读一个字段 `capacity`（必须是大于零的整数，`capacity:2.5`、`capacity:0`
  都被**拒绝**并说明；别的类别写这个字段不读也不报错）。没写就是**装不下任何东西**的仓库，而不是一个被塞了
  一个谁也没写的尺寸的仓库。
* **拖动入库**：松手时看掉落物**落在哪一格**（位置是点，格子由它取整得到），从**最高瓦片层往下**找那一格上的
  仓库——与画面上看到的一致。进得去就进容器、地上那件**随即从索引里消失**（帧末从存储里消失，正在遍历的回调
  手里的指针仍然有效）；进不去（满了）就留在放开的地方，并且**在错误色里说出来**；落在空地上就是普通放下。
  `PointerDrag::end()` 因此返回 `Stored` / `Refused` / `Left` / `Nothing`，并留下最后一件的类别与 id
  （它已经从层里消失，消息只能靠这里记住的身份）。
* **点击看内容**：点击**不落在可拖的东西上**时就是一次点击——所有仓库都被问一遍（落在它身上的那个打开或收起，
  其余的把面板收起来），面板画在**地块的右下角**：标题行 `WAREHOUSE   1 / 4`，然后一件一行
  `drop #1 chunk   x1`（空的就是 `EMPTY`）。三语言都有。
* **实测（真机无头 1280×720，夹具层 20×12、2 个瓦片层、3 个仓库、1 个掉落物）**：把掉落物从屏幕
  `(642,372)` 拖到仓库 `(375,482)` 松手 → HUD 变成 `STORED drop #1 chunk`，按颜色数**地上的掉落物像素
  从 198 个变成 0 个**（它进了容器），容器里 1 件；再点一下那个仓库 → 面板出现在它右下角，写着
  `WAREHOUSE   1 / 4` 与 `drop #1 chunk   x1`。两张截图就是这两步。
* **验证**：新增 `test_warehouses` **6 用例 / 106 断言**（容器：容量/剩余/满、只收下放得下的、按到达顺序列出、
  取走返回实际数量且空槽消失、没有内容的 id 与 0 件都不收、容量调小不丢东西；draginto：整件收下或什么都不变、
  收一个掉落物实体；click：点它开、再点关、点别处关、只数落在它身上的；仓库：是场景地块不是实体地块、
  不 tick、容量来自条目、2×2 覆盖四格、点击按格判定；拖动：拖到仓库上入库且地上消失、满了拒绝且留在原地、
  落在空地上就是放下；定义器：读容量、拒绝非整数/零/负数、别的类别写了不读）；`test_text` 347 → **357 断言**
  （三语言的五条新文案）。套件 **30 个测试**全绿（release / debug / asan / tsan / server-only 30/30、
  no-renderer 11/11、Ore 13/13）。
* **表与公开面**：本体表 789 → **806 节 / 2499 → 2553 符号 / 9620 → 9773 重定位**（release，
  1 288 432 → 1 306 545 B = 1.25 MiB；debug 5982 / 20384 / 26831 / 3.77 MiB），指纹不变

  align 分布 `{1:132, 2:64, 4:7, 8:83, 16:446, 32:42, 64:32}`，向宿主索取的符号仍是 **161** 个。
* **还没有的东西**：① **没有数据说"哪里该有仓库"**——`warehouse::` 说得清"有这么一种仓库"，说不清"在这一层

### M2 交付状态（十三）：本地化名称，与 40–100 像素/格的相机（已落地）

设计者的要求（§1.29、§1.30 的原话）："添加本地化名称功能，以及限制摄像头缩放为40px-100px"。

* **一个查找，界面各处**：`content_label()`（`mine/content_name.h`，M2.15 引入）现在被界面上**每一处**显示
  内容名字的地方点名使用——游戏里唯一的入口是 `MineApp::content_name(种类, id)`（`games/mine/include/mine/app.h`）：
  ① 世界视图 HUD 的格子那一行（被指的地块与拖动中都算），② 仓库面板的标题与每一行（M2.15 已经是），
  ③ 内容列表的每一行，④ 沙盒调色板的每一行（名字在左，`种类 #id` 在右，id 仍在——存档与日志用它），
  ⑤ 入库那条 HUD 消息（`已入库 drop #1 chunk`），⑥ 沙盒自己的格子读数与格子标签（状态栏 `L0 floor #1 DIRT`，
  以及格子上放得下时画的那个标签——放不下时仍然退回 `#id`，那是存档与日志用的数字）。
  **"界面上显示内容名字"因此只有一条实现**，改一次这些地方一起改；找不到的那一处（沙盒状态栏与格子标签）
  正是**重出截图时看出来的**：图先拍，字随后对不上，就把代码改了。
* **没写名字的内容显示它的 id**：这条回退规则没有变（`t2d::Locale::text` 对没有的字符串回它被问的 id），
  所以夹具的 `chunk`、`scrap` 仍然显示它们自己的 id——**用夹具的那些截图因此没变**（本体内容都有名字，
  夹具没有），只有本体内容出现的地方变了。
* **种类自己的词不跟语言走**（`content_kind_name`：`ore`、`warehouse`…）：它们是引擎的词汇，写在文档、
  日志与 `engine.api` 里，界面上的 `warehouse #1 石头仓库` 正是"引擎的词 + 设计者的名字"。**设计者说不需要
  它们跟语言走**（M2.16 的答复），所以种类词永远是引擎的英文词汇，界面上一眼分得清哪一半是谁的。
* **相机的缩放范围**：`mine/view_limits.h`（`kMinViewZoom = 40.0f` / `kMaxViewZoom = 100.0f`）在
  `MineApp` 构造时交给世界相机（`set_zoom_limits`），所以**每一条**改缩放的路都落在同一对数字里——
  启动参数 `--view`、进层的自动取景、`+`/`-`、滚轮；相机自己仍然是"缩放没有变化就不移动视野"
  （`Camera2D::zoom_at` 在范围顶端照样成立）。40 是还能看清并点中一格的下限，100 是一格占满屏幕的上限。
  **这两个数是常量，不是内容数据**：设计者说不需要每层的范围（M2.16 的答复），`view_limits.h` 因此是
  唯一一处写着它们的代码。
* **实测（真机无头 1280×720，夹具层 20×12，64 像素/格起步）**：连按 12 次 `-`（不设限会是
  64 × 0.8¹² = 4.4 像素/格）→ HUD 写着 **`40.00 PX/CELL   32x18`**（1280 ÷ 40 = 32 格），木箱上那个灰叉
  实测 **31 → 19 像素**（19 ÷ 0.484 = 40）；连按 12 次 `+`（不设限会是 64 × 1.25¹² = 931 像素/格）→
  **`100.00 PX/CELL   14x8`**，同一个灰叉 **48 像素**（48 ÷ 0.48 = 100）——两头都停住，48 ÷ 19 = 2.5
  正是 100 ÷ 40。`--view 10,6,5`（要 5）开机就是 `40.00 PX/CELL`。
* **装不下的图：限制赢**：故事的 100×100 层按 40 像素/格是 4000×4000 像素，1280×720 的窗口要"看到整张图"
  得约 12 像素/格——进层取景只能到 **40**，实测 `LAYER 0 100x100 … 40.00 PX/CELL   32x18`。这是设计者给的
  范围的直接结果（§1.30），不是缺陷：范围是设计者定的，取景只能到它允许的地方。
* **名字的证据**：英文 HUD `CELL 1,9   floor #1 DIRT   1x1 AT 1,9 MIRRORED`——**DIRT 是大写的**，而注册表里

### M2 交付状态（十四）：双击选中带容器的地块，内容显示在界面最上方居中（已落地）

### M2 交付状态（十五）：`.ecfg` 的 `__include`（已落地）

设计者的要求（§1.32 的原话）："为ecfg添加__include: #file 功能，加载时可以加载其他ecfg文件的内容放入
include所在的位置解析"。

* **它是"位置"，不是"字符串"**：展开在**解析之前**做——一行 `__include: #<路径>` 被那个文件的行**替换**掉，
  再交给原来的解析器。所以 include 出来的内容与直接写在那儿**完全一样**：同样的键唯一、同样的缩进规则、
  同样的报错。内容包里的每个内容文件、`ui.ecfg`、`mod.ecfg`、沙盒读的那几份，走的都是这条路
  （`EcfgDocument::load` 现在会解析 include）。
* **缩进就是位置**：被包含的文件**顶格**写，落进来时缩进到 `__include` 那一行的缩进。于是同一份片段既能放
  在顶层、也能放进 `item::` 表里——这正是"把一个文件拆成几份"的用法（`docs/MODS.md` §0 有例子）。
  `<< ... >>` 文本块的内容**原样**搬过去：那是值，缩进它会把值改掉。
* **每一处失败都指得出来**：读不到（`__include 'x.ecfg' cannot be read (from …)`）、成环（a 引 b、b 引 a
  → `is already being read … (a loop)`）、嵌套超过 **16** 层、`#` 后面没写路径——四种都报**文件 + 行号**；
  被包含文件里的**语法错误**也指回它自己（解析器数的是展开后的行，报告时换回原来的文件与行）。
* **纯文本的 `parse(text)` 会拒绝 include**，并说清原因（那段文本没有可以相对的文件）：内存里的文本没有
  目录，替它猜一个是不对的。知道自己在读文件的调用方用 `load`（相对文件自己）或新的重载
  `parse(text, base_directory, error)`。
* **被包含的文件自己也能 include**（递归展开，链上查环），所以"包 → 章节 → 条目"这种三层拆分是自然的。
* **片段可以自己声明**（设计者 M2.18 的第三条，值三选一）：`__not_main` 是 `"skip"` 时 `load` **跳过**这个
  文件——没有文档、**也没有错误**（`ecfg_skipped(error)` 就是问这个；重载照样跳过）；是 `"true"` 时**拒绝**，
  错误直说"include 它，不要单独加载它"；是 `"false"`（或不写）时是普通文件。两个布尔字面量 `true`/`false`
  等价。**别的值一律报错**，不会被猜成 `false`。include 这条路不经过 `load`（展开器自己读文本），所以片段
  照常能被 include。它是文件自己的属性——**不跟着内容走**：被 include 的文件即使写着 `"skip"`，包住它的
  主文件仍然是一个可以加载的主文件（有单测钉住，否则每个带片段的包都会拒绝加载）。
  引擎自带的三条加载路径（内容包扫描、模组宿主、沙盒重载）都按这个字段跳过文件；`EcfgDocument::main()`
  让别的调用方也能问出文件自己说了什么。与 `_` 前缀分工：名字让**包扫描**不去读它，字段让**直接加载**失败
  或跳过，两道保险。
* **片段的名字以 `_` 开头**（`_parts.ecfg`、`_ores/stone.ecfg`）：内容包扫描时这样的文件或目录**不是内容
  文件**，因为它们既会被自己读一遍、又会被 include 一遍，同一份内容就会注册两次（实测过：不跳过时那条
  内容会被报成"不是一个内容类别"）。片段照样能被 include——扫描看名字，展开看 `__include`，两件事分开。
* **验证**：`test_ecfg` 12 → **22 用例 / 128 → 154 断言**（十个新用例：顶层与表内、文本块原样、递归、相对
  文件、读不到、成环、写法不对、纯文本拒绝、被包含文件里的语法错误指回它自己）；`test_content_pack`
  **16 用例 / 253 断言**（两个新用例：一个包里的内容文件 include 另一个、include 不到时报出文件名）；
  套件 **31 个测试**全绿（release / debug / asan / tsan / server-only 31/31、no-renderer 11/11、Ore 13/13）。
* **表与公开面**：本体表 **857 节 / 2674 符号**里 t2d 部分 57 → **58** 个（多的是新的 `parse` 重载），
  引擎公开面 83 → **84** 个（A 层 38 → **39**，`engine.api` 里加了那一行），启动器仍然报 0 个越界符号；
  向宿主索取的符号总数 162 → **163**。
* **验证跑得更快了**（设计者 M2.18 的第四条）：`tools/verify.sh` 把七个目标（六个预设 + Ore）**并行**跑
  （每个构建树彼此独立），每个目标内部再用 `ctest -j` 并行，作业数按核数在目标间平分（`VERIFY_JOBS` 可覆盖）。
  实测同一台机器上：原来串行 **约 190 秒**，现在 **27 秒**（都建好时）到 **53 秒**（含增量构建）——约 3.5–7 倍。
  并行也暴露了两个**真的会打架**的地方并修掉了：工具的 ABI 探针目录原来按"在构建什么"命名（两个预设同时跑同一个
  测试就是同一个目录，一个把另一个正在链接的目录删掉），`/tmp/codetab-names.txt` 是固定名（两个进程互相截断）。
  现在两者的名字都带**本次运行的令牌**。日志在 `build/verify/`。
* **还没有的东西**：① include 不做"只包含一次"——同一个文件被两处 include 就是两份，和 C 的 `#include` 一样；
  ② 没有通配（`#parts/*.ecfg` 不行），要哪份写哪份；③ 路径可以写 `..`、也可以写绝对路径——内容文件是给
  设计者的工具，不是一个沙箱；④ 分层更多的是编辑器的事：展开后的行号只出现在错误信息里。

### M2 交付状态（十六）：层定义器的 `place_block`（已落地）

设计者的要求（§1.33 的原话）："在层定义器中添加place_block字段，可以在指定位置放置具有指定属性的方块，格式为
place_block:: / placement1:: / x:111... subobject:: / container:: / items:["aaa",100,"bbb",100]"。

* **一条放置就是一行数据，落在它说的那一格**：`kind` + `content`（与 `scatter` 同一对字段）、`layer`（默认 0）、`x` 与 `y`
  （**两个都要写**——一格有两个坐标，原话里的 `x:111...` 后面的省略号我读作"还有别的字段"）、`subobject:: container::
  items:[名字,数量,…]`。位置是**固定**的（这正是它与 `scatter` 的分工：一个说"哪里"，一个说"多少"）。
* **它是第三个创建器**：地板 → **放置** → 散点。放在散点之前，占住的那一格散点就不会再落上去（与"一个格子一个
  瓦片层只放一个东西"同一条规则）；地板在它之前，所以放置的东西站在已经铺好的地板上。
* **`subobject::` 是引擎的词**：今天只有 `container::`（将来机器输入侧、需求提交箱是同一层里的别的子对象），
  别的名字**直接报错**，不会被忽略——与 `size::`、`floor::` 一样，引擎定义的表里不认识的键是错误。`items` 是"名字、
  数量"成对的扁平数组：奇数个、名字不是字符串、数量不是正整数，都在读文件时报错。
* **物品名字在这里不解析**：放在层里的数据只说名字，**世界建这一层时**才拿注册表去查（模组能改名、能加物品，

  装进去的东西是真的在那儿（同一屏也是 §1.31 的选中方框）。
* **验证**：`test_layer_rules` 23 → **25 用例 / 807 → 828 断言**（一条完整放置读成什么、五种写法错误各自的措辞）；

### M2 交付状态（十七）：`building` 子对象、放置前的判断、定义属性与存档属性（已落地）

设计者的两段要求（§1.34、§1.35 的原话）："创建building子对象，包含对应地块的所需材料，建造时间，建筑分类（存储，
加工，开采等，后续需要），提供建造相关的接口，包含can_place等方法在放置前判断对应的位置是否符合放着的条件，例如
钻头必须放置在矿物上等"；"我们需要让地块和子对象的属性分为定义属性(例如1个仓库容量是100这一类固定属性)和存档属性
（例如一个仓库里面有什么）并让他们区分起来，其中定义属性不可以在层设置中覆盖，地图上的所有同种地块读取同一份定义
属性，参考享元设计"。

* **`building` 是一个子对象，和容器并列**：内容条目下 `building:: materials:[…] time:5 category:"extraction"`；
  地块用 `SceneTile::building()` 回答。分类是引擎的词（storage / processing / extraction），不认识的名字在读文件时
  报错——与 `subobject::` 的其它名字同一条规矩。
* **`can_place` 是放置前的询问**，在 `MineLayer` 上（它才知道地图）：格子在不在图上、瓦片层有没有、那一格是不是空的、
  以及内容自己的条件。今天唯一的内容条件是设计者给的例子：**钻头必须站在矿上**（同一格更低瓦片层里有矿），层构建时
  对钻头强制，不合就进构建报告并跳过这一块。
* **定义属性 / 存档属性按享元分开**：`TileDefinition` 是**一份共享记录**（容量、掉头、图片、挖掘力、硬度、掉落、
  `building`），活过所有层；地块实例只存自己的状态。地块通过新的 `SceneTile::definition()` 拿到那一份——固定属性
  从它读，不拷贝。**层设置写不进定义属性**：`place_block` 的 `container::` 只认 `items`，写 `capacity:` 报错。
* **设计者的四条答复**（M2.20 收尾）：① "一次完善"——**容量改成定义属性**：`Warehouse::capacity()` 现在读它那一份
  定义（`definition()->capacity`），**没有 setter 了**，容器只是按定义建出来，运行时改不动；② "等后续加入"——
  `can_place` 的更多规则等设计者给；③ "等后续开发"——建造本身（扣材料、走时间、完工）等后续；④ "完善"——
  **单测补上了**（见下）。
* **验证**：`test_mine_types` 15 → **17 用例 / 191 → 224 断言**（`building` 从数据读出来是什么；同一内容的两块地块
  `definition()` 与 `building()` 是**同一个指针**——享元；不是建筑的内容 `building()` 是空）；`test_world` 15 →
  **16 用例 / 153 → 168 断言**（`can_place` 的四类回答各自的措辞：空位、已占、出图、瓦片层不存在；**钻头要矿**
  的两条分支；层构建时对钻头强制、报告里点名）；套件 **31 个测试**全绿（release / debug / asan / tsan / server-only
  31/31、no-renderer 11/11、Ore 13/13）。

## 10. 非目标（工程边界）

* 不做 3D、体素、复杂光照、大规模粒子。（"多边形风格"指的是 2D 贴图的美术风格，不是 3D 建模。）
* 不做玩家角色/化身：没有角色贴图、角色移动、角色碰撞，也没有"出生点"（§1.11）。
* 不做矢量多边形渲染：贴图是图片资源（PNG），"多边形"是美术风格，不是渲染方式（§1.10）。
* 不预设任何玩法内容（战斗、敌人、经济、成就……）——需要就由设计者提出。
* M1 界面只支持 ASCII 大写（框架内置 5×7 位图字体）；中文界面需换字体，等设计者确认（§7.12）。
* 不做横版动作（重力 / 跳跃 / 单向平台）：框架里曾经的横版演示已删除，游戏是平面俯视无重力。
* 不引入第二套网络栈，联机一律走 Tile2D 的 `ILink`（共享内存 / KCP）与同一套分帧握手。
* 沙盒是开发工具，**不是第三种玩法模式**：它不含内容、不做地形生成、不对布局文件承诺存档兼容
  （见 `docs/SANDBOX.md`）。

## 11. 术语

| 术语 | 含义 |
|---|---|
| 层（Layer） | 矿场的一层，一张独立地图实例，带资源/结构/需求描述 |
| 地块（Tile） | 地图中占据格子的**固定物体**（地板、矿物、机器…），可以占 1 格或 2×2、3×3、2×3 等；基类 `mine::types::Tile`（§1.12） |
| 场景地块（SceneTile） | 构成矿场的地块（场景、矿物、地板）：**仅在需要时更新**，没有每帧成本（§1.13） |
| 实体地块（EntityTile） | 功能地块（机器…）：**继承场景地块**，在此之上**每 tick 或每 xx 秒更新**，节奏由地块自己持有（§1.13、§1.14） |
| 渲染翻转（random_reverse） | 地块基类上的开关：为真时地图初始化随机决定是否**左右翻转渲染**（50%），只影响渲染（§1.14）；**由内容作者在数据里写**，`mirrored` 不进存档（§1.15） |
| 地板（Floor） | 其他东西站上去的那一层：`SceneTile` 的子类，只多一个 `is_floor()` 标记；`floor::` 表声明（§1.16） |
| 矿物（SingleOre） | 一格一块、可以挖出来的东西：`SceneTile` 的子类，只多一个 `is_ore()` 标记；`ore::` 表声明，散点生成器撒的就是它（§1.19） |
| 散点生成器（ScatterRule） | 层创建器的一种（`layer::` 的 `scatter::`）：在指定瓦片层上按**平均密度**撒指定内容，**最小/最大数量**夹住结果，**地板限制**决定哪些格子可用（`mine/layer_rules.h`） |
| 本体内容 | 游戏自己带的内容，`games/mine/content/`，加载顺序的第一段，无需参数（§1.17） |
| 层描述（LayerSpec） | 层的数据表示：地图形状 + 要放的内容（kind、名字、瓦片层、锚点、占地）；故事模式来自设计者数据，无尽模式由种子生成 |
| 层规则（LayerRule） | 故事模式里一层的描述：`size::`（多大、几个瓦片层）与 `floor::`（地板创建器，规则 `full_flash`）；**`layer::` 的书写顺序就是矿场顺序**（`mine/layer_rules.h`） |
| 世界（MineWorld） | 一座矿场：种子、层形状、生成器，以及**当前被进入的那一层**（`mine/world.h`）；层数可以很多，内存里只有一层 |
| 层实例（MineLayer） | 一层矿场：地图格（`ContentGrid`）+ 地块（`mine::types`）+ 块索引 + 这一层自己的骰子；两条推进路径都在它身上 |
| 需求（Demand） | 层目标：通过某种提交方式提交指定原料或产物；完成即推进 |
| 提交渠道（Submit channel） | 接收提交的机制（规则由设计者定义，实现提供抽象） |
| 会话（Session） | 一次游戏运行：世界类型 + 角色 + 种子（+ 连接信息） |
| 上帝视角（God view） | 没有化身的操作方式：输入驱动相机与指针，作用在地图上（§1.11） |
| 多边形风格（Polygon style） | 贴图的**美术风格**：低多边形、平色块、硬边；贴图本身仍是图片资源（§1.10） |
