# 单层沙盒 —— 内容调试工具

> **沙盒不是游戏模式。** 设计者确认的玩法模式是故事与无尽（`docs/GAME_DESIGN.md` §1.9）。沙盒是
> **开发期工具**：只渲染**一层**，没有需求、没有层间推进、没有服务端、没有存档流程。它存在的唯一
> 理由是：在内容数据还没写完的时候，就能看见数据长什么样。

沙盒里**没有任何游戏内容**：面板列出的每一项都来自设计者的 `.ecfg` 数据文件，引擎不解释名字的
含义。不给 `--content` 时网格保持为空，并在屏幕上直说“未注册任何内容”，而不是显示一个编造的示例层。

---

## 1. 它能回答的问题

| 问题 | 沙盒里的答案 |
|---|---|
| 我的数据文件解析了吗？ | 状态栏的 `RELOAD: +a -b` 或 `RELOAD FAILED: 文件:行:列: 原因` |
| 引擎给每个名字分了什么 id？ | 内容面板每行右侧 `structure #3`（id 按 kind 各自从 1 开始，按文件顺序分配） |
| 哪些东西能放到格子上？ | 面板里只出现“占格子”的 kind（当前是 structure / machine）；item / recipe / layer / channel 不出现 |
| 表名写错了会怎样？ | `RELOAD: ... 1 UNKNOWN TABLE(S), FIRST 'structurs'`，不会静默忽略 |
| 我把一条内容删了，旧布局会怎样？ | 相关格子标红并显示“已缺失”，**不会**把它的 id 交给现在占用这个数字的别的内容 |
| 我在文件中间插了一条，id 全变了，旧布局还认吗？ | 认。布局按名字重定位（见 §4） |
| 一层地图能分几个瓦片层？ | `--tile-layers N`：每层一张独立网格，自下而上绘制；画笔写入当前层（`[` `]` 切换），`--fill-layer all` 一次把整叠铺出来 |
| 几百格见方的图能看全吗？ | 能。`--grid 512x512` 后按 `C` 整图入框（缩到 1 像素/格以下，按块采样绘制），滚轮/`+`/`-` 放大回格子级 |
| 大地图会不会越看越卡？ | 不会：绘制只走**视口覆盖的格子**（相机给的范围），成本随屏幕而不是随地图；状态栏 `VIEW` 行给出像素/格与可见格数，`STORAGE` 行给出地图格实际占用的内存 |
| 打开就想看某个位置？ | `--view x,y[,zoom]`：直接停在某格、某个缩放，而不是整图入框 |
| 这一层大概长什么样？ | `--fill scatter` 用注册到的内容铺一层（同 seed 完全可复现） |

## 2. 运行

```sh
# 空沙盒：证明“没有内容就什么都不画”
./build/debug/games/mine/mine_game --world sandbox --start 1

# 看一份内容数据：面板列出它注册出的全部内容
./build/debug/games/mine/mine_game --world sandbox --start 1 \
    --content <你的内容.ecfg>

# 直接看“这一层可能长什么样”，并导出/读回布局
./build/debug/games/mine/mine_game --world sandbox --start 1 \
    --content <你的内容.ecfg> --fill scatter --seed 7 \
    --layout /tmp/layer.bin

# 几百格见方、多层：512x512、四层各铺一份，并直接停在 (200,150) 放大 20 像素/格看
./build/debug/games/mine/mine_game --world sandbox --start 1 \
    --content <你的内容.ecfg> --grid 512x512 --tile-layers 4 --fill-layer all \
    --fill scatter --view 200,150,20
```

从开始界面进入也可以：`世界` 行左右切到 `沙盒`，然后选 `打开沙盒`。

选中沙盒时只有一行动作 —— 主持 / 加入不会出现，因为沙盒是一个本地层，后面没有服务器：

![开始界面里的沙盒](images/sandbox_menu_zh_hans.png)

| 选项 | 含义 |
|---|---|
| `--world sandbox` | 直接进沙盒（等价于界面里切到沙盒） |
| `--content <path>` | 内容数据文件，**可重复**（多个文件按顺序注册） |
| `--pack <file.ecfg>` | 加载一个纯 ecfg 内容包（可重复）：一个文件就是一个包，可选 `pack::` 头。见 `docs/MODS.md` |
| `--packs <dir>` | 内容包目录：每个 `*.ecfg` 是一个包（可重复；缺省加载工作目录下的 `packs/`） |
| `--mods <dir>` | 模组包目录（可重复）：包里的内容与本体内容进同一个注册表，本体先注册。见 `docs/MODS.md` |
| `--grid <WxH>` | 这一层多大，默认 `40x24`（地图尺寸是 §7 待设计者给的内容，所以它是参数） |
| `--tile-layers <n>` | 这张图有几个**瓦片层**，默认 1（上限 32） |
| `--layer <n>` | 启动时停在哪一层；画笔写这一层 |
| `--view <x,y[,zoom]>` | 启动时相机停在格子 (x,y)，可选缩放（像素/格）；不给就是整图入框（`C` 的初始状态） |
| `--fill-layer <n|all>` | 填充写进哪些层，默认当前层；`all` 每层各铺一份（散点每层用不同种子，所以三层不一样） |
| `--fill <none\|bands\|scatter>` | 调试填充：`bands` 每个内容一条横带（当色卡看），`scatter` 随机散布 |
| `--seed <n>` | `scatter` 的种子；同种子同结果 |
| `--layout <path>` | 启动时读入的布局文件，也是 F2 写出的位置 |
| `--save-layout <path>` | 退出时写出布局（脚本化运行用，等价于按 F2） |
| `--dump-layer <0\|1>` | 退出时把这一层按文字打进日志（等价于按 F4） |

## 4. 为什么 F5 重载是安全的

内容按名字注册、运行时用数字 id（`docs/GAME_DESIGN.md` §6）。在数据文件中间插一条内容，它**后面
所有同类内容的 id 都会 +1** —— 如果布局只记数字，重载后每个格子都会悄悄变成另一样东西。

所以重载分三步：

1. **先全部解析，再动任何东西**：任何一个文件解析失败，注册表与网格都保持原样，只报错。
2. 用新文件重建注册表（先清空，删掉的内容才真的消失，id 也才是全新注册会给出的那套）。
3. **按名字**把每个已放置的格子重新指向它的内容（`ContentRemap`）。id 变了不算变化；内容没了就把
   格子标成“已缺失”：**名字留在表里、格子内部保留它当初的 id 但对外一律显示 `#0`**，所以既不会把它
   交给现在占用这个 id 的别的内容，也不会在内容回来时丢掉它——回来的那条内容按名字把格子修好。

## 5. 真机验证：id 变了，层没变

用仓库里的三个占位数据文件（名字是 `placeholder_*`，**不是游戏内容**，只是为了能验证工具本身；
`v2` = 在 structure 表最前面插一项，`v3` = 删掉 `placeholder_ore`）跑三次，`--dump-layer 1` 把每一层
打进日志后逐格比对：

```sh
cd tile2d
D=games/mine/tests/data
# A：铺一层散点并存盘
./build/debug/games/mine/mine_game --world sandbox --start 1 --headless --frames 3 \
    --content $D/placeholder_content.ecfg --fill scatter --seed 1 --save-layout /tmp/a.bin
# B：换成 v2（id 整体位移）读入 A 的布局；C：换成 v3（少一条内容）读同一个布局
./build/debug/games/mine/mine_game --world sandbox --start 1 --headless --frames 3 \
    --content $D/placeholder_content_v2.ecfg --layout /tmp/a.bin --dump-layer 1
./build/debug/games/mine/mine_game --world sandbox --start 1 --headless --frames 3 \
    --content $D/placeholder_content_v3.ecfg --layout /tmp/a.bin --dump-layer 1
```

| 运行 | 数据文件 | 做了什么 | 结果 |
|---|---|---|---|
| A | v1（6 项） | `--fill scatter --seed 1` 铺 241 格，`--save-layout` 存盘 | 241 格 |
| B | v2（7 项，在 structure 表**最前面**插了一项） | 读入 A 存的布局 | **241 格，0 缺失**；坐标、kind、名字与 A 完全一致；**148 个格子的 id 变了**（structure 全部 +1，machine 不变；例如 (0,5) 的 `placeholder_wall` 1 → 2） |
| C | v3（5 项，删掉了 `placeholder_ore`） | 读入同一个布局 | **190 格，51 缺失**；缺失格子仍显示 `placeholder_ore`、对外 id 为 0，**没有一格拿到新的数字** |

B 里 id 移动的例子：`(0,5) placeholder_floor 2 → 3`、`(0,4) placeholder_ore 3 → 4`。
C 里 51 个格子全部保留名字、id 为 0。

同一件事在**三个瓦片层**上再跑一遍（同样 `--seed 1 --tile-layers 3 --fill-layer all`，A 里 687 个格子
分布在三层：241 / 225 / 221）：

| 运行 | 数据文件 | 结果 |
|---|---|---|
| A | v1（6 项） | 三层各铺一份散点，687 格，存盘 |
| B | v2（structure 表最前面插一项） | 读入 A 的布局：**687 格 / 0 缺失**，层号、坐标、kind、名字与 A 完全一致，**404 个格子的 id 变了** |
| C | v3（删掉 `placeholder_ore`） | 读入同一布局：**549 格 / 138 缺失**，缺失分布在三层（51 / 35 / 52），全部保留名字、对外 id 为 0 |

布局文件把**每一层**都写进去（magic `MSB3`），所以层数变了或某层的内容被删掉，都会在载入时被如实报告。

## 6. 它不做什么（边界）

* 只有**一层**，没有层间通道、没有层推进、没有需求（这些要等设计者的内容清单，见 `docs/GAME_DESIGN.md` §7 与 M3）。
* **不生成**任何内容：`bands`/`scatter` 只是把已注册的内容铺开，不是地形生成器。
* 不做存档：布局文件（magic `MSB3`）是**调试文件**，格式随工具变化，不承诺兼容；游戏的存档是另一件事（`docs/GAME_DESIGN.md` §6）。
* 布局文件里的层数上限是 32（`TileMap::kMaxLayers`）；再多的层不是一张图，是一次分配。
* 地图边长上限：沙盒 1024（布局文件是外部输入，不许它要到一次 GB 级分配），游戏自己的地图格
  `ContentGrid` 4096（4096×4096×4 字节 = 64 MiB 一层）。
* 缩得太小时画的是**采样**而不是全部格子：可见格子数 × 层数超过四边形预算（16384）时，每个四边形
  覆盖 `ceil(sqrt(总数/预算))` 格，颜色取这块正中间那一格的内容。这是“缩略图”，不是“少画了一些格子”——
  放大回去就是逐格绘制（`VIEW` 行会告诉你现在是哪个状态）。
* 每帧顶点从 upload ring 的一段里分配，**段满则整批丢弃**（屏幕会空、日志会报错）；mine 给沙盒配了
  4 MiB 的段（`AppConfig::upload_segment_size`），状态栏 `VIEW` 行在真的丢了四边形时会直接写出来。
* 没有撤销、没有矩形框选、没有复制粘贴、没有多格笔刷。
* 面板里不显示设计者字段（`yield:3` 之类）—— 引擎不解释它们；要看内容请直接看数据文件。
* 颜色不是美术：格子的颜色由**名字的哈希**决定（同名恒同色，重载不变色），美术资源属于设计者的内容。

## 7. 大图与相机

玩法要在几百格见方的图上跑（`docs/GAME_DESIGN.md` §2），沙盒是这套东西的第一个使用者：

* **相机是框架类型**：`t2d/core/camera2d.h`。视口 + 世界中心 + 缩放（像素/世界单位；格子游戏里就是
  像素/格）。`screen_of`/`world_of` 互为精确逆，`zoom_at(锚点, 倍数)` 保证指针下的世界点不动，
  `fit()` 带边距把整张图框进视口，`clamp_to()` 让有界视角停在图边（图比视口小时居中），
  `visible_cells()` 给出视口覆盖的半开格子范围——渲染剔除就用它。它纯数学、无 GPU、无窗口，
  单测 `test_camera2d`（7 用例 / 1986 断言）在 0.1 ms 内跑完。
* **地图格是 4 字节**：`mine::ContentGrid` 每格一个 32 位的内容引用（20 位 id + 4 位 kind + 1 位
  “内容已消失”），层按第一次写入分配，已放置计数是计数器。改造前沙盒每格存一个 `std::string`：
  37 字节，且每放一个格子一次堆分配。
* **绘制只走屏幕**：可见格子由相机给出，超过四边形预算就按块采样（`draw_step_for()`）；低缩放下
  网格线与格子标签自动关闭（它们本来就会比屏幕更密）。

真机数字（Intel Arc Pro 130T/140T，debug 构建，离屏 1280×720，`--fill scatter --fill-layer all`）：

| 地图 | 格子数 | `STORAGE` | 每帧 | 进程峰值 RSS |
|---|---|---|---|---|
| 40×24 × 1 层 | 960 | 3 KiB | ~9 ms | 100.5 MB |
| 512×512 × 4 层 | 1.05M | 4096 KiB | ~10 ms | 100.4 MB |
| 1024×1024 × 8 层 | 8.4M | 32768 KiB | ~9 ms | 116.6 MB |

改造前同一组命令：512×512×4 峰值 134.5 MB、20 帧 2.25 s；1024×1024×8 峰值 414.6 MB、20 帧 5.30 s
（帧时间被每帧两次全图遍历主导）。现在帧成本随屏幕走，不随地图面积走。

## 8. 与工程约束的关系

沙盒是“内容未定时也能往前推”的产物，它反过来验证了三件工程约束：

* **内容数据驱动**：面板里出现的每一项都来自数据文件，代码里没有任何资源/结构/机器名字。
* **注册按名字、运行用数字 id、每份存档自带 name→id 表**：布局文件就是按这个策略存的，§5 是它的
  真实往返证据（含“内容消失”和“id 整体位移”两种最坏情况）。
* **缺失内容要被报告而不是被重映射**：`已缺失` 的格子、`UNKNOWN TABLE(S)` 的表名、解析失败的
* **内容可以来自外部模组包**：`--mods` 加载的模组与本体内容共用一套注册与 id 规则，同名内容报冲突而不合并；状态栏的 `MODS` 行显示加载了几个包、几个原生模块、注册了多少内容。
  行列号，全部出现在屏幕上，而不是只写进日志。
