# 代码表：让 C++ 模组能改本体

本文回答一个问题：**为什么现在的 C++ 模组做不了事，怎么让它们能做几乎所有 C++ 能做的事——包括改掉本体内部的函数和类。**

这不是设想：表文件格式、工具链、内存合并运行时都已经落地，测试用真实编译器编出来的目标文件跑通了
"模组覆盖本体函数"与"模组覆盖虚函数、本体的虚调用改道到模组"两件事（§7 是实测数字）。

---

## 1. 现在弱在哪里（都有出处）

| 弱在哪 | 证据 |
|---|---|
| 模组只能**注册名字**，不能定义行为 | `mine/mod_api.h` 的 `MineModApi` 只有 6 个函数：log / register_content / find_content / content_name / mod_value / mod_int。没有 tick、没有世界、没有事件 |
| 内容文件里的"逻辑"没人读 | `mine/types/tile_definition.cpp` 只读 `image` 与 `random_reverse`，其余字段全是设计者的、引擎不看 |
| **不能修改已有内容**，只能追加 | `register_declared_content()` 遇到同名报"已注册、未替换"；没有 patch / override / remove |
| 不能改本体的**函数** | 共享库是 `dlopen` 进来的：本体内部的调用在链接时就绑定好了，后加载的库改不了它 |
| 编译一个模组没有工程支持 | `mine_mod_sdk` 是构建树里的 INTERFACE 目标，没有 `install()`/`export()`，外面的人只能自己猜 include 与链接参数 |

**根本原因**：本体是一个"已经链接完的程序"，模组是一个"后加载的库"。链接发生在模组存在之前，
所以本体内部怎么调用自己，模组说什么都不算。

## 2. 方案：把链接推迟到启动时

不再"先链接本体、再加载模组"，而是：

    本体源码 --(系统编译器)--> 目标文件 --(codetab)--> 本体.codetab ┐
    模组源码 --(系统编译器)--> 目标文件 --(codetab)--> 模组.codetab ┤
                                                              ├--(CodeImage 运行时)--> 一张符号表
                                                              ┘                          一段段内存
                                                              --(重定位)--> 一次**启动时**的链接

关键的两点，都在编译器开关里，不在我们的代码里：

* **`-fsemantic-interposition`**：让"调用另一个翻译单元里的函数"**保留成一条重定位**，而不是被内联或
  常量折叠掉。没有它，本体里 `a()` 调 `b()` 会变成一段已经算好的机器码，**没有东西可改**。
  实测（clang 22，x86-64）：

      extern "C" int base_value();          callq base_value   →  R_X86_64_PLT32   base_value - 4
      int g_counter;                        movq (%rip),%rax   →  R_X86_64_REX_GOTPCRELX  g_counter - 4

* **`-ffunction-sections -fdata-sections`**：每个函数、每个全局各占一节，合并时才能"留一个、丢一个"。

于是**合并 = 一次链接**，而"覆盖"就是符号解析的先后顺序：

| 动作 | 在运行时里是什么 |
|---|---|
| **拼接** | 每个模块的节都被放进同一片地址空间 |
| **覆盖** | 后加入的模块里**强定义**同名符号 → 赢；**所有**模块（包括本体自己）对该符号的重定位都指向赢家，并写进合并报告 |
| **注入** | 谁都没定义过的名字，直接加进符号表 |
| **合并（弱）** | `weak` 定义（内联函数、模板实例、vtable、typeinfo）**先到先得**，不报冲突——一个 C++ 程序只有一份 |
| **包装** | `CodeImage::find_previous(name)` 给出"被自己顶掉的那个定义"，模组因此能调用原件 |

**同一份定义不一定只有一份字节**：内联函数、模板实例、vtable 是 `weak`，每个用到它的翻译单元都会吐一份
COMDAT 拷贝——而编译器**允许**这些拷贝长得不一样（它按各自的上下文决定把多少东西内联进这个函数体；实测
GCC 在 `-O3` 下给 `std::__format` 的 sink 吐出了 253 字节与 744 字节两个版本，指令都不一样）。所以合并按
**组签名 + 节名 + 字节**认"这是同一份定义"：字节一致才只留一份，不一致就各留各的，符号仍然先到先得。
**被丢掉的拷贝，它的重定位跟着一起丢**——重定位只补自己那一节的字节，把别人的偏移写到自己身上就是越界。
（0.1.0 的 Release 包第一次跑不起来，报的 "a relocation runs past the section" 就是这里：小的那份被留下，
大的那份的重定位照写不误。）

**为什么这能改类**：vtable 是数据，它的每一项都是**重定位**。合并时那条重定位指向谁，虚调用就去谁那里。
所以模组重定义一个**非内联的虚函数**，本体的虚调用会自动改道到模组——不需要任何补丁、不需要改 vtable 指针。
（内联虚函数是 `weak`，会被合并成先到的那份，改不了；这是 C++ 的 ODR，不是运行时的毛病。）

## 3. 表文件（`.codetab`，格式版本 1）

一个表就是"编译器吐出来的东西"的容器，没有自己的主张：

    头部 104 字节   magic "CODETABL" / 版本 / 机器 / 三个计数 / 五块的偏移与长度
    名字块          所有名字挤在一起，NUL 结尾，别处存偏移
    节表            每项 32 字节：名字 / 类型 / 标志 / 对齐 / 在字节块里的偏移 / 大小
    符号表          每项 32 字节：名字 / 所属节 / 种类 / 绑定 / 值 / 大小
    重定位表        每项 32 字节：节 / 类型 / 偏移 / 符号 / 加数
    字节块          所有节的原始字节，按各自对齐排好
    元数据          `id= name= version= requires=` 四行，外加 `abi=` 一族键（构建它的编译器说的 ABI，§5.6）

* 只装**运行时真的需要**的节（`SHF_ALLOC`）：注释、调试信息、符号表本身都不进表。
* 元数据里的 `requires` 就是模组声明的依赖（"我期待和谁合并"），合并报告用它。
* 机器码是机器相关的，所以头部记了机器（目前只有 x86-64）与版本；**读不懂就拒绝**，不猜。

## 4. 工具链：`codetab`

    codetab build <源码...> -o <输出.codetab> [--id mine --version 1.0] [--requires engine@1.0 --api engine.api]
    codetab pack  <目标文件...> -o <输出.codetab>   # 构建系统自己管编译开关时用它
    codetab dump  <表文件>            # 节 / 符号 / 重定位 / 元数据，全列出来
    codetab api   --surface engine.api <表...>   # 它向引擎要什么，以及能不能要
    codetab dumphead <表文件> [-o <名字.h>]      # 它定义了哪些符号，按作用域分组
    codetab abi   <表文件>...                    # 它是什么 ABI 编出来的（§5.6）
    codetab abi   --record <文件>                # 把"本机这次构建的 ABI"写成一份记录（启动器用）

它**驱动系统编译器**（默认 `c++`，可用 `--compiler` 换），把编出来的目标文件读进来、打包成表。
打包之前它还会**问编译器这次构建的 ABI 是什么**（一个生成的探针 TU，§5.6），把头文件按内容哈希，
写进表的元数据；`--no-abi` 可以不要这份记录，`--headers` 让 `pack` 知道对象是照哪些头文件编的。
它自己加上的开关就是 §2 里那两条，外加 `-fno-stack-protector`（让表自足，不必回调运行中的程序要
`__stack_chk_fail`）。`--exceptions` 可以打开异常，但**展开还没有注册**（§8）。

编译器仍然是唯一的编译器：这里没有第二个 C++ 前端，也不会有。

## 5. 运行时：`t2d/core/code_table.h`

    CodeImage image;
    image.add(本体表);            // 先加入的：它的定义会被后面的顶掉
    image.add(模组表);
    const CodeImageReport& report = image.load();
    auto produce = image.function<int()>("mine::produce");   // 或 mangled 名

`load()` 按顺序做五件事，每一步的失败都写进报告，**不让一个坏模块带崩整张图**：

0. **先看它是什么编出来的**：`requires` 与 **ABI 记录**（§5.6）在放置任何东西之前校验——依赖没人提供、
   版本对不上、指纹与本体不同、共享头文件内容不同、CPU 缺特性，这个模块**整体拒绝**，报告逐条指名，
   它定义的符号一个都不进符号表。
2. **解析符号**：先建全局符号表（强/弱规则见 §2），再把每个模块的每个符号解析成最终地址；
   本体之外的未定义符号去**运行中的程序**里找（`dlsym(RTLD_DEFAULT, ...)`）——这就是表回调引擎的方式。
   `_GLOBAL_OFFSET_TABLE_` 由运行时自己回答（模块自己的 GOT）。
3. **重定位**：x86-64 的 `R_X86_64_64 / PC32 / PLT32 / 32 / 32S / GOTPCREL / GOTPCRELX / REX_GOTPCRELX`。
   不认识的类型**报错**，不按"大概是这个意思"写下去。GOT 槽在放置时预留、重定位时填。
4. **收尾**：可执行的那片改成 `PROT_READ|EXEC`——填完之后还能写的代码是没人需要的口子。
5. **构造**：跑每个模块的 `.init_array`（C++ 全局对象的静态构造），**在所有重定位填完之后**，按加载顺序。

模块没放置成功、或重定位失败，就被标为失败：**它定义的符号不会留在符号表里**——一张还提供"跑不起来的
代码"的符号表比没有更糟。

两处工程细节，都是"真实程序"逼出来的：

* **一个模块只用一片内存**：代码在前，数据隔一页在后。调用与 GOT 读取都是 **32 位位移**，所以一个模块
  自己的东西必须互相够得着——分成两片 mmap 时它们可能相隔几 GB。代码那一半在重定位填完后 `mprotect`
  成只读可执行，数据那一半保持可写。
* **够不着的调用走桩**：引擎的函数在程序自己所在的位置，可能离表的代码超过 2 GiB（`call` 只能写 32 位
  位移）。这时运行时在调用点旁边放一个 `jmp qword ptr [rip+2]` 桩，桩里是完整地址——这就是链接器的
  PLT 在做的事。实测中它真的被用到了：表里的游戏代码调用宿主的 `t2d::log_enabled` 时超距，靠桩接上。

## 5.5 公开面与版本：引擎说了算的只有清单里的符号

引擎/本体一改就可能悄悄弄坏模组。答案分两层：**符号层面有一张公开面清单**（`engine.api`，见
`docs/ENGINE_API.md`），**版本层面按这张清单分档**。

* `engine.api` 第一行是 `engine <major>.<minor>`，之后每行 `<层> <mangled 符号> <模块>`。A 层（`t2d/core`、
  `t2d/text`）**冻结**；B 层（`t2d/render`、`t2d/net`、`ore/*`）**提供、但会随实现改**；C 层（本体内部、
  沙盒、模组宿主）**拒绝**并指名。平台符号（libc / libstdc++）不属于我们的 API，校验时不问。
* 版本规则（`t2d::api_verdict`）：模块**只用了公开面之内**的引擎符号 → 整个 major 之内都放行、一声不响；
  **越出公开面** → 版本相同则静默放行，相差一个 minor **警告后仍然加载**（`kUnlistedMinorRange = 1`），
  再远**拒绝**；**major 不同一律拒绝**，与用了什么无关。
* 表里的 `requires`：`id` 或 `id@版本`。`id` 只要求"有人在"；`id@1.0` 要求**正好**是这个版本。
* 启动器 `declare_host("engine", <engine.api 里的版本>)`，并在**放置任何模块之前**校验 `requires`：没人提供、
  或版本对不上，这个模块被拒绝，报告写明"它按 X 版本编的，这里的是 Y"，它的符号一个都不进符号表。
* 越界与否是**实测**的，不是猜的：加载后看每个模块真正向宿主索取的符号（`host_symbols`），逐个查清单。
  实测本体自己的表要宿主 **82** 个引擎符号（`t2d::` 57 + `ore::` 25），**全部**在清单内（启动器报告 0 个越界），
  另有 **77** 个平台符号（`-fno-exceptions` 之后不再有异常机制那批，原来是 92）。
* 三处执行同一个规则：`codetab build|pack --api engine.api` 在**写表之前**拒绝越界（本体自己的表就是这么
  打的，越界即构建失败）；`codetab api --surface engine.api <表>` 检查已经存在的表；启动器在加载时再查一遍，
  并逐个指名越界的符号。

工具链那边就是 `--requires engine@1.0 --api engine.api`。

## 5.6 构建时统一 ABI：工具链就是 ABI（已落地）

`engine.api` 管的是**名字**（哪些符号能碰），版本规则管的是**差多远**。两者都看不见"名字一样、东西不一样"：
同一个 `std::string` 在两种 ABI 下是 8 字节与 32 字节，同一个类多一个虚函数就换了槽位，同一个 `struct` 多一个字段
就换了布局。所以表里还带一份**构建记录**（`abi=` 一族键），由工具链**问编译器**得到：

* 一个生成的探针 TU，用**与模块相同的** `-std/-O/-I/-D` 编译并运行，逐行打印事实：`_GLIBCXX_USE_CXX11_ABI`、
  `_GLIBCXX_DEBUG`、`__GXX_ABI_VERSION`、`__SIZEOF_*`、`sizeof`/`alignof`（`std::string`、`vector`、`map`、
  `function`、`filesystem::path`、`optional`、`variant`…）、CPU 特性宏；
* **必须一致**的事实（决定布局的）排序后取 FNV-1a 64 就是**指纹**；**可以不同**的（`NDEBUG`、`__EXCEPTIONS`、
  `__GXX_RTTI`、`__OPTIMIZE__`、sanitizer、构建传的 `-D`）只记录、只报告，不拦；
* **头文件按内容哈希、按相对路径记**（源树与 dev 包的路径不同、内容相同）；系统头不记——C++ 库的 ABI 是事实；
* **CPU 特性对照本机**（`__builtin_cpu_supports`），不是对照本体：为更窄的机器编的代码到处都能跑。

加载时：**指纹相同 → 完全合并**（`-O0` 的模组和 `-O3 -DNDEBUG` 的本体就是一个程序，差异只在日志里说一句）；
**指纹不同 → 拒绝并指名事实**（`_GLIBCXX_USE_CXX11_ABI: 0 here, 1 there`）。**没有"降级加载"**：类型不同的模块
调用本体时算出来的地址就是错的，少给权限只会让它安静地错（完整分析：[`ABI.md`](ABI.md) §1.5）。

**本体自己也走同一扇门**：`games/mine/CMakeLists.txt` 用 `codetab build` 编 `mine.codetab`，启动器自己那份记录
由 `codetab abi --record` 写成 `engine.abi`，与 `engine.api` 一起随可执行文件走。于是模组作者只要用 dev 包里的
`codetab` 与头文件，指纹天然一致——**这就是"构建时统一 ABI"**。实测：debug 与 release 两个预设的
`engine.abi` 与 `mine.codetab` 指纹相同（`f3ca0b9119e3c2cb`），演示模组也是。

## 6. 与现在这套模组系统的关系

* 现在的 **`dlopen` 原生模组**（`mine/mod_api.h` 那套 C ABI）继续有效：它是"我只想注册点内容"的轻量形态。
* **表模组**是"我要改东西"的形态：同一门语言、同一个编译器，但拿到的是整个程序的符号。
* 两者可以共存：宿主先合并表，再把内容注册的 C ABI 交给 `dlopen` 模组。
* 内容侧的补丁/覆盖（改 `image`、改配方字段）与代码侧的覆盖是两件事，前者仍走 `.ecfg` 的加载顺序，
  后者走表合并顺序；两者都**报告**自己改了什么。

**热重载**：`dlopen` 模组今天可以在帧之间卸载重载（F5）。表模组**不承诺**热重载——表一旦被放置，
函数指针、vtable 指针、静态数据地址就已经散进整个程序，换掉一张表等于把那些指针全变成悬空的。
所以：**表模组在启动时合并，改表要重启**；将来若要热重载，只能整进程重来（或限定"没有任何指针逃逸"的
子集，那是另一个设计）。用户已确认这条取舍可以接受。

## 7. 已经落地并验证的部分

代码：

* `t2d/core/object_file.h`：读 ELF64 目标文件（节、符号、重定位、COMDAT 组）。
* `t2d/core/code_table.h`：表格式（读写）、`from_objects()`（多目标文件合并成一张表）、`CodeImage`（合并、重定位、运行）、
  `ApiSurface` / `api_verdict`（公开面与版本规则）。
* `t2d/tools/codetab`：工具链——`build`（驱动编译器再打包）、`pack`（只打包）、`dump`、`api`（查公开面）、
  `dumphead`（把表定义的东西导成给编辑器看的索引）。
* `engine.api`：公开面清单（82 个符号：A 层 38 / B 层 44），随可执行文件走。
* `games/mine/src/main.cpp`：**启动器**——收集表（`mine.codetab`、`--table`、`packs/*.codetab`）、合并、
  校验公开面与版本、调用入口符号 `mine_game_main`。
* 测试 `t2d/tests/test_code_table.cpp`：**21 用例 / 274 断言**，fixture 由构建过程用真实编译器编出目标文件；
  其中 7 个用例是 ABI 的（指纹相同即合并、指纹不同即拒绝并指名、头文件改动、CPU 特性、没有记录、工具链端到端、
  销毁映像跑析构）。
* 测试 `games/mine/tests/test_mine_table.cpp`：**3 用例 / 17 断言**——**游戏自己的代码进表**：
  `games/mine/src/registry.cpp`（本体真实源文件，不是副本）被编成表，合并后运行，回调宿主，
  再被一张模组表覆盖掉一个函数。

实测（本机 x86-64，GCC 16 / clang 22 均可）：

| 证明了什么 | 数字 |
|---|---|
| 表能被读回、字节一致 | 往返用例 120 断言（整个 `test_code_table` 274 断言） |
| 合并后能跑 | `use_base()` = 11 |
| **模组覆盖本体函数，本体的调用改道** | 合并模组后 `use_base()` = **101**；报告 1 条覆盖（`base_value`，my_mod ← vanilla） |
| 覆盖后还能调用原件（包装） | `find_previous("base_value")` = 10 |
| 回调运行中的程序 | 表里没定义的 `strlen` 由宿主解析，`length_of("hello")` = 5 |
| 没人定义就报告并拒绝该模块 | 未解析名单 = `nowhere_to_be_found`，模块不加载 |
| **改类：覆盖虚函数，虚调用改道** | `machine_output()` 25 → **97**（9×10+7：虚函数与普通函数都被换掉） |
| 弱符号合并而非冲突 | vtable `_ZTV…` 与 typeinfo `_ZTI…` 都是 weak，合并后只报 2 条强覆盖 |
| 静态构造在重定位之后运行 | `.init_array` 跑过，全局值 = 41 |
| 工具链端到端 | `codetab build` 两个源文件 → 13 节 / 16 符号 / 3 重定位 / 5 个可覆盖名，约 26 ms |
| **版本不符就拒绝加载** | 要求 `mine@2.0` 的模组被拒（报告同时写出 2.0 与 1.0），要求 `mine@1.0` 的正常合并；没人提供的依赖同样拒绝 |
| **本体代码进表并运行** | `mine_core` 的 `registry.cpp` 编成表：注册两个 item（id 1、2）、重复注册 id 不变，`game_probe()` = 110 |
| **模组覆盖本体表里的函数** | 加一张模组表后 `game_probe()` = **112**，报告 1 条覆盖（`game_bonus`，game_mod ← mine），`find_previous()` = 5 |
| **表回调宿主** | 表里没定义的 `host_service` 与 `t2d::log_enabled` 由宿主解析（后者超距，走了桩） |
| **整块本体进表，可执行文件变启动器** | 表由工具链编（`codetab build`）：release **772 节 / 2485 符号 / 7600 重定位 / 1.00 MiB**；debug **5211 / 21410 / 12999 / 3.18 MiB**。启动器合并后调用 `mine_game_main`，游戏照常跑（窗口、Vulkan、内容、多语言） |
| **构建时统一 ABI** | 本体表与启动器记录同指纹（`f3ca0b9119e3c2cb`）；`-O0`/`-O2`/`-O3 -DNDEBUG` 三种构建指纹相同、完全合并；另一个 `std::string` ABI、头文件改动、CPU 缺特性三种情形**拒绝并指名**（§5.6、[`ABI.md`](ABI.md)） |
| **一份定义两个函数体不再出错** | GCC 在 `-O3` 下把同一个 vague linkage 函数吐成 253 与 744 字节两份（指令都不同）：两份各自入表、符号先到先得；被丢掉的拷贝连同它的重定位一起丢，越界即构建失败 |
| **模组表端到端** | `--table mods/demo_mod/mod.codetab`：`mine_game_banner` 被 `demo_mod` 顶掉（报告 1 条覆盖），游戏自己的调用改道，输出从 `Mine, unmodified` 变成 `Mine, modded` |
| **公开面执行** | 本体表向宿主索取 82 个引擎符号 + 77 个平台符号，越界 0 个；`codetab build --api engine.api` 在构建期就拒绝越界 |

打包（同一个构建出两个 zip）：release 包 = 启动器 + 表 + `engine.api` + 界面文本 + 本体内容包 + 着色器 + `packs/` 模板，
`--strip-all` 之后约 0.9 MiB；dev 包 = 头文件（含生成的 `config.h`）+ `engine.api` + 本体表 + `codetab` 工具 + 模板 + 文档。
两个包都从"只有一个解压目录"的环境里实跑过：`0 error(s)`，界面文本来自包内的 `assets/text/ui.ecfg`。

预设：tile2d **debug / release / asan / tsan 25/25**、no-renderer **11/11**、Ore **13/13**。

## 8. 边界（写在明处）

* **只有 x86-64 / ELF**。表里是机器码，换机器要重新编表；运行时会明确拒绝别的机器。
* **不支持 TLS**：线程局部变量要有自己的动态链接器支持，表不带（会报错，不静默）。
* **异常与展开未注册**：本体表现在由工具链编（默认 `-fno-exceptions`），所以它**不再带异常机制**；
  带 `.gcc_except_table*` 的表在**构建期就被拒绝**（`--exceptions` 是作者说"我知道"，那时只提示一行）。
  真机上的后果仍然是"抛出即终止"：
  实测比这句话更糟：**抛出点与 `catch` 在同一个函数里也一样终止**（`terminate`，exit 134），
  因为丢掉的是帧描述、留下的是异常表（丢弃规则是精确名匹配，`-ffunction-sections` 下节名带后缀）。
  本体自己的表（Release）里今天就有 8 条 `__cxa_begin_catch`、199 条 `_Unwind_Resume` 重定位。要支持得做 `__register_frame` 与
  `.gcc_except_table` 的处理（实测与方案见 [`ABI.md`](ABI.md) H1）。
* **内联函数 / 模板实例 / vtable 本身改不了**（它们是 weak，先到先得）。**非内联**的函数与虚函数可以。
* **不是沙箱**：表和 `dlopen` 一样以游戏权限运行，能做游戏能做的一切。这是能力，不是安全边界。
* **一个模块失败不影响别的模块**：报告 + 跳过；但一个模块内部"一半重定位成功"是不允许的（该模块整体不加载）。
  启动器自己的政策更严：**任何模块报错就拒绝启动**（`if (!report.clean()) return 1`）——它是被指名加载的，
  "少加载一个"不是它该做的决定。
* **名字对得上不等于东西对得上**：公开面查的是符号名，类型布局、vtable 形状、内联函数体、编译开关都不查。
  十二处实测（段错误、静默错值、一个进程两种行为）与分步方案见 [`ABI.md`](ABI.md)。
